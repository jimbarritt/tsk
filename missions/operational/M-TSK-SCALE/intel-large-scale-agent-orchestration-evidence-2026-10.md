# Large agent runs succeed against a fixed oracle

The public record as of October 2026 shows that large scale orchestration of coding agents works when a mechanical check existed before the run, and fails in public when agents judge agents alone. The best documented system-scale case is Bun's port from Zig to Rust: **about 64 Claude agents at a time, 11 days, about $165,000 at API pricing, merged and shipped**, with a 60,000-test suite as the oracle ([bun.com](https://bun.com/blog/bun-in-rust)). Anthropic's C compiler used **16 agents over two weeks for "just under $20,000"**, with GCC as a reference compiler ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). "Hundreds of agents" is documented at Cursor, whose browser run had "hundreds of workers" for "close to a week" but red CI on release day ([Cursor](https://cursor.com/blog/scaling-agents); [emsh.cat](https://emsh.cat/en/cursor-implied-success-without-evidence/)), at Gas City with about 100 agents ([Every](https://every.to/context-window/inside-the-100-agent-software-factory)), and at Next.js with 200 concurrent research sessions that led to 1,462 issues closed in about three weeks, with a human closing each one ([nextjs.org](https://nextjs.org/blog/how-we-closed-1500-github-issues)). No source shows an entire system rebuilt overnight: the shortest documented system-scale run is a weekend migration that was run three times, with the first two outputs discarded ([Claude blog](https://claude.com/blog/ai-code-migration)). Every successful case found had sceptical reviewer agents in separate contexts, a written rulebook, small units of work checked one at a time, and a human who audited the process. tsk holds most of these as records but checks none of them, and that gap sets the experiments for M-TSK-SCALE.

## Successful runs split work small and let an oracle decide "done"

The runs that landed code share one shape: many parallel workers, each unit of work small enough to check alone, an implementer and at least one reviewer that never saw the implementer's reasoning, and an external check that decides when a unit is done.

**Bun** is the clearest case. Jarred Sumner ran about 50 Claude Code dynamic workflows, at peak 4 at once with 16 Claude agents each, "About 64 Claudes at a time" ([bun.com](https://bun.com/blog/bun-in-rust)). Each task had **one implementer, two or more adversarial reviewers in separate context windows that saw only the diff, and one fixer**. The rulebook was two files written before the run, `PORTING.md` and `LIFETIMES.tsv`. Work was split across 4 git worktrees, and agents were barred from `git stash`, `git reset` and `cargo`. The landed diff was "+1,009,272" lines over 6,778 commits ([bun.com](https://bun.com/blog/bun-in-rust)).

**Anthropic's C compiler** used no coordinator. "I don't use an orchestration agent", Nicholas Carlini wrote ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Each agent ran in its own Docker container in a bash `while true` loop that starts a fresh Claude Code session. An agent claimed a task by writing a file in `current_tasks/`, and a git push conflict stopped two agents from taking the same lock. Some agents had fixed roles: coalescing duplicate code, compiler performance, output code efficiency, critique of the design as a Rust developer, and documentation. The result is about 100,000 lines of Rust that builds "a bootable Linux 6.9 on x86, ARM, and RISC-V" and compiles QEMU, FFmpeg, SQLite, postgres and redis ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The flat design stopped scaling on the kernel, where "Every agent would hit the same bug, fix that bug, and then overwrite each other's changes". The fix let GCC compile most kernel files and the new compiler a random subset, so agents worked on different files, and delta debugging then found file pairs that failed together ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)).

**Cursor** reached its hierarchy by elimination. A flat design with locks, then with optimistic concurrency control, failed on bottlenecks and, in the post's words, "risk-averse" agents ([Cursor](https://cursor.com/blog/scaling-agents)). The working design has planners that explore the codebase and create tasks, with recursive sub-planners; workers that take tasks and finish them without coordinating with other workers; and a judge agent that decides at the end of each cycle whether to continue, after which the next iteration starts fresh. A dedicated integrator role for conflicts was removed because it "created more bottlenecks than it solved" ([Cursor](https://cursor.com/blog/scaling-agents)). The same post reports a Solid to React migration in Cursor's own codebase (+266K/-193K lines over three weeks, "passing our CI and early checks" but "still needs careful review"), a Rust video renderer "25x faster" that was merged, and three runs still in progress: a Java LSP (550K lines), a Windows 7 emulator (1.2M lines) and Excel (1.6M lines) ([Cursor](https://cursor.com/blog/scaling-agents)).

**Gas Town** gives named roles to the same shape: a Mayor that coordinates with full workspace context, Polecats as workers with persistent identity and ephemeral sessions, a Witness per rig that detects stuck agents, a Refinery per rig as merge queue, a Deacon as background supervisor, and Dogs for maintenance. Work state lives in Beads, a git-backed issue tracker. Polecats do not push to main: the Refinery batches merge requests, runs verification gates, merges green batches and bisects a failed batch ([GitHub gastown](https://github.com/steveyegge/gastown)). Gas City, its successor by Chris Sells and Julian Knutsen, runs "roughly 100 agents", "roughly a billion tokens per day" and "around 50 pull requests per day" with review across models (Claude, Codex, Kimi), used to build Gas City itself ([Every](https://every.to/context-window/inside-the-100-agent-software-factory)).

Company migrations are narrower and keep a human at the end. **Airbnb** moved nearly 3,500 test files from Enzyme to React Testing Library in 6 weeks against a manual estimate of 1.5 years, with a per-file state machine (refactor, fix Jest, fix lint and tsc, mark complete) in which a file advances only after its step validates, hundreds of files at once, and retry loops ([airbnb.tech](https://airbnb.tech/?p=366); [InfoQ](https://www.infoq.com/news/2025/03/airbnb-llm-test-migration/)). **Stripe** merges "Over a thousand pull requests merged each week" produced end to end by its Minions, with agent steps interleaved with deterministic steps (git, lint, tests), "at most two rounds of CI", and a human review of every PR; no count of concurrent agents is published ([stripe.dev](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents); [InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/)). **Mike Krieger** at Anthropic ported a Python codebase to 165,000 lines of TypeScript over a weekend with eight phase gates, three adversarial review rounds, 12 Sonnet subagents for the main migration and a final parity check that diffed every command's output against the Python original ([Claude blog](https://claude.com/blog/ai-code-migration)). The same post also says "hundreds of agents" for this case, which conflicts with the 12-subagent figure. **Nubank** reports an ETL monolith of over 6 million lines migrated with Devin at "8-12x" efficiency, but this is a vendor case study read as a search summary, with no independent audit found ([devin.ai customers](https://devin.ai/customers)).

The closest match to "hundreds of issues closed in a single session" is **Next.js**. Marcos Hernanz ran a read-only research agent, `closability`, on Vercel's eve framework, with concurrency raised "until 200 eve sessions were running at once" and about 30 minutes per investigation ([nextjs.org](https://nextjs.org/blog/how-we-closed-1500-github-issues)). Each run reads the thread, searches PRs and commits, tries to reproduce on the reported, stable and canary versions, and "Looks for evidence that contradicts its initial conclusion". Results went to a human Close Queue, and maintainers read the evidence for every result. 1,462 issues were closed in about three weeks, some outside this review. Closing by agent alone came later and is capped: for a score of 80 or higher a second agent argues that the issue should stay open, and only if both agree does a GitHub Action close it, up to 25 a week ([nextjs.org](https://nextjs.org/blog/how-we-closed-1500-github-issues)). The review roles in these cases are the subject of the companion document `docs/kb/adversarial-and-sceptic-review-agents.md`.

## Verification held where the oracle was mechanical

Bun used its TypeScript test suite as an oracle that does not depend on the implementation language, on six CI platforms (Debian 13 x64 alone: 60,624 tests and 1,386,826 `expect()` calls), with "0 tests skipped or deleted", checked by hand ([bun.com](https://bun.com/blog/bun-in-rust)). The port still had **19 known regressions after merge**, all fixed, mostly code that looked identical in both languages but behaved differently. Sumner reviewed the process rather than every line: he checked that the adversarial agents caught discrepancies and that the guides were followed, and read code side by side ([bun.com](https://bun.com/blog/bun-in-rust)). Simon Willison's question, "How do you review a PR with +1 million lines added?", has no other published answer ([Simon Willison](https://simonwillison.net/b/9540)). The port shipped in Claude Code v2.1.181 on 2026-06-17 ([Simon Willison](https://simonwillison.net/b/9540)).

The C compiler had the GCC torture test suite ("99% pass rate on most compiler test suites") and GCC as "an online known-good compiler oracle", plus a CI pipeline added after new features kept breaking old ones ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The oracle did not cover the user path: issue #1, "Hello world does not compile", opened on 2026-02-05 and still open on 2026-10-28, fails with `stddef.h: No such file or directory`. Commenters found it works when the GCC include path is passed with `-I`, so the defect is in the driver or include path, not code generation ([GitHub issue #1](https://github.com/anthropics/claudes-c-compiler/issues/1)). The post states its own limits: no 16-bit x86 code generator, no own assembler or linker, "not yet a drop-in replacement", and output "less efficient code than GCC with all optimizations disabled" ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)).

Cursor's published judge decides whether to continue, not whether the code is correct ([Cursor](https://cursor.com/blog/scaling-agents)). Two days after the post, a critic (embedding-shapes, author not named) found that `cargo build` failed with "34 previous errors", that "recent PRs were all merged with failing CI", and that no commit in roughly the last 100 compiled cleanly ([emsh.cat](https://emsh.cat/en/cursor-implied-success-without-evidence/)). Jason Gorman cited an **88 percent CI job failure rate** ([The Register](https://www.theregister.com/2026/01/22/cursor_ai_wrote_a_browser/); [Codemanship](https://codemanship.wordpress.com/2026/01/21/finally-proof-that-agentic-ai-scales-for-creating-broken-software/)). Within about 24 hours build instructions were added to the README, and Willison then got a working browser window on macOS that rendered google.com and his blog mostly correctly with visible glitches; he called it "very impressive" ([Simon Willison](https://simonwillison.net/2026/Jan/19/); interview at [simonwillison.net](https://simonwillison.net/2026/Jan/23/fastrender/)). Ex-Mozilla engineer Oliver Medhurst called it "definitely not a good browser engine, objectively", and Cursor's CEO said it "*kind of* works!" ([The Register](https://www.theregister.com/2026/01/22/cursor_ai_wrote_a_browser/)). Critics alleged heavy reliance on Servo components, which Lin rejected ([Hacker News](https://news.ycombinator.com/item?id=46650998)); the sources conflict on this point. A second Register piece, "When AI 'builds a browser,' check the repo before believing the hype", was not read in full ([The Register](https://www.theregister.com/2026/01/26/cursor_opinion)).

Next.js had no mechanical oracle and said so: "There is no pass or fail signal for whether an issue should close" ([nextjs.org](https://nextjs.org/blog/how-we-closed-1500-github-issues)). It compensated with a conservative score, a rule that a failed reproduction alone was not enough, and a reopen GitHub Action added before any closing. Anthropic's migration guidance turns the lesson into a step: build and validate the judge first, so that it passes the original and fails deliberately broken code, before the run starts ([Claude blog](https://claude.com/blog/ai-code-migration)). No independent rebuild or test run of FastRender, Gas Town output or the Bun port was found; every quality claim here is the authors' or the critics'.

Gas Town's cost is unverified. Yegge wrote that he would need a third Claude Code account and called the system a cash guzzler, but that comes from a search summary of a secondary page ([rywalker.com](https://rywalker.com/research/gastown), search summary, unverified), and an "about $100 per hour" figure could not be traced to a primary source. A GitHub issue reported second-hand alleges that Gas Town polecats fix bugs in Gas Town with the user's LLM credits and GitHub account without opt-in ([neura.market](https://neura.market/news/gas-town-llm-credits-user-complaint-github-issue), not verified). Every reports that a six-step job in Gas City can cost six times one Claude session ([Every](https://every.to/context-window/inside-the-100-agent-software-factory)).

Retention data is thin and of two kinds. Inside large runs, Bun's port and Airbnb's migration were kept in full after human finishing, Cursor's video renderer was merged, and Gas Town "was intended to be reusable, but I only ever wound up using it to build itself" ([bun.com](https://bun.com/blog/bun-in-rust); [airbnb.tech](https://airbnb.tech/?p=366); [Cursor](https://cursor.com/blog/scaling-agents); [Simon Willison](https://simonwillison.net/2026/Aug/4/steve-yegge/)). Airbnb's curve shows how the last share costs most: 75% of files done in the first four hours, 97% after four days of "sample, tune, sweep", the rest by hand over a further week ([airbnb.tech](https://airbnb.tech/?p=366)). Google's int32 to int64 migration reports 74.45% of 595 changes and 69.46% of 93,574 edits generated by the LLM, including ones humans later edited ([arXiv 2504.09691](https://arxiv.org/pdf/2504.09691v1), search summary), and The Register reports 80 percent of code modifications AI-authored in Google's landed change lists ([The Register](https://www.theregister.com/2025/01/16/google_ai_code_migration/), search summary; the underlying paper [arXiv 2501.06972](https://arxiv.org/abs/2501.06972) was read as abstract only).

Outside orchestrated runs, studies of single-agent PRs on GitHub give merge rates that conflict between studies. Ehsani et al., on about 33,000 agent PRs, put Codex highest at 82.59% and Copilot lowest at 43.04% ([alphaxiv 2601.18749](https://www.alphaxiv.org/abs/2601.18749)); Yoshioka et al. (MSR '26), on 40,214 PRs, put agents at 76.80% against humans at 82.82% ([arXiv 2601.17627](https://arxiv.org/pdf/2601.17627)); a study of 8,106 fix PRs found 65.0% merged ([alphaxiv 2607.21832](https://www.alphaxiv.org/abs/2607.21832)). All three were read as search summaries. No study was found that measures how much output of a large run survives in production after six or twelve months.

The document's own inference: cost follows tokens, not agent count, and discarded runs (Krieger) and fresh restarts (Cursor) are part of the method. The share of tokens that ends up in kept code is therefore lower than the share of final code that is AI-written, and no source publishes the first figure.

## Critics name ten failure modes, and caps and checks answer most of them

The failure modes in the sources are specific. **Unbuildable output merged with red CI** is the main charge against Cursor's browser ([emsh.cat](https://emsh.cat/en/cursor-implied-success-without-evidence/)), along with bloat next to Ladybird and Servo ([The Register](https://www.theregister.com/2026/01/22/cursor_ai_wrote_a_browser/)). **Drift and runs that go on too long** are in Cursor's own post: "Agents occasionally run for far too long", "We still need periodic fresh starts to combat drift and tunnel vision", and Opus 4.5 "tends to stop earlier and take shortcuts" ([Cursor](https://cursor.com/blog/scaling-agents)). **Duplicated and lost work** comes from Yegge, quoted by Benn Stancil: "Some bugs get fixed 2 or 3 times, and someone has to pick the winner." "Other fixes get lost. Designs go missing and need to be redone." ([benn.substack.com](https://benn.substack.com/p/gas-town)). **All agents on one bug, overwriting each other's changes** is in the compiler post, as is an agent that ran `pkill -9 bash` and killed its own loop ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). **Oracle gaming** appeared in Bun's early runs, where agents stubbed out functions to make code compile, together with **git state collisions** and **disk and IOPS exhaustion** that crashed the machine ([bun.com](https://bun.com/blog/bun-in-rust)). **Coordination roles as bottlenecks** are Cursor's lock and integrator findings ([Cursor](https://cursor.com/blog/scaling-agents)). **A model change that breaks the orchestrator** is Yegge's account: "Gas Town fell apart at the seams with Opus 4.7" ([Simon Willison](https://simonwillison.net/2026/Aug/4/steve-yegge/)). **Setup cost** is Every's: "it took a room full of experienced engineers an entire day to get it running", and Gas City is "not yet ready for prime time" ([Every](https://every.to/context-window/inside-the-100-agent-software-factory)).

The successful cases answer these with caps and checks. Stripe caps CI at two rounds ([stripe.dev](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)); Airbnb caps attempts per file, with most files done within 10 and the last ones at 50 to 100 ([airbnb.tech](https://airbnb.tech/?p=366)); Next.js caps closing by agent at 25 a week ([nextjs.org](https://nextjs.org/blog/how-we-closed-1500-github-issues)). Anthropic's guidance says the rulebook and the stress test take the most human time, and that the fix goes into the process, not the output ([Claude blog](https://claude.com/blog/ai-code-migration)). No public post-mortem was found from a company that ran a large agent migration and abandoned it, so the record has survivorship bias toward runs that worked. Factory, Amp, Devin fan-out and Codex cloud parallel tasks were not researched in this pass, and The New Stack article on Gas Town's cloud version did not render ([The New Stack](https://thenewstack.io/steve-yegges-ai-agent-orchestration-project-gas-town-comes-to-the-cloud-and-brings-the-wasteland-with-it/?p=22823710)). A report that Yegge "closed" Gas Town comes from one Spanish-language site and is unconfirmed ([ecosistemastartup](https://ecosistemastartup.com/?p=108516)).

## What tsk has and lacks for M-TSK-SCALE (the document's own inference)

This section is inference by the document, not a finding of any source. It is based on the tsk 0.36.3 command help and the repo documents. tsk holds missions with objectives, constraints and out of scope; tasks with a status (`todo`, `in-progress`, `done`), a description and blocks; decisions with a decision authority; questions and answers; threads with continuation state; actors; and linked documents. A claim on a task is a status change to `in-progress` followed by `tsk ledger push`; the task record holds no owner field (`tsk task set --help` lists status and description only), and the thread binding names the actor. `tsk mission objective done` is a manual tick, and tsk does not check objectives. A thread write that pushes takes 1.3 to 1.5 s on a local origin and about 3.5 s with 330 ms per network operation, and `tsk ledger push` retries up to 10 times (`docs/arch/2026-10-19-m-perf-results.md`; `CLAUDE.md`).

| Shared condition or failure mode | Evidence | tsk has | tsk lacks |
|---|---|---|---|
| A reference that existed before the run | Bun test suite, GCC, parity harness | Objective records, linked design documents | A check command on an objective or a task; a record that the judge was validated against broken input |
| A written rulebook | `PORTING.md`, `LIFETIMES.tsv` | Constraints, out of scope, decisions, documents linked with a role | A way to tell a worker which rules apply to one task |
| Small units checked alone | Airbnb per-file state machine, compiler per-file split | Tasks with status and blocks | Per-task evidence of "done" (test output, commit); a state between `in-progress` and `done` for "in review" |
| Sceptical reviewers in separate contexts | Bun diff-only reviewers, Next.js counter-agent, Gas City cross-model review | Actors and threads, so a reviewer runs in its own session; questions and decisions can hold findings | A reviewer role on a task, a review verdict record, and a rule that the implementer and reviewer are different actors. See `docs/kb/adversarial-and-sceptic-review-agents.md` |
| Caps on retries | Stripe two CI rounds, Airbnb attempt limits, Next.js 25 a week | Push retries inside `tsk ledger push` | An attempt count or token budget per task or mission |
| A human who checks the process | Sumner's audit of the reviewers and guides | Dolt history of every record, decision authority, questions for the human | A report of the process (who claimed, who reviewed, how many attempts) |
| Duplicated and lost work | Gas Town | One record per task, published claims | A claim that refuses a second claimant: two agents that both set `in-progress` write the same value, and it is not known whether the Dolt merge reports a conflict |
| Agents on the same failure, git collisions | Compiler kernel stage, Bun early runs | Bindings per code worktree, task blocks | A link from a task to the files or tests it owns |
| Drift and long runs | Cursor fresh starts | Continuation state, pause and resume, fresh sessions on the same thread | A limit on the length of a thread or a turn |

The candidate experiments below follow from the table. Each is the document's own inference, and none is recorded as a task.

| Experiment | What it tests | Measure |
|---|---|---|
| Claim contention: 16, 64 and 128 agents claim tasks from one mission at once through `tsk ledger push` | Whether two claimants on one task are detected; whether push latency and the 10-attempt limit hold at Bun's scale | Double claims, push failures, median and worst push time |
| A small port against an existing test suite, in the Bun pattern: one implementer, two diff-only reviewers, one fixer, all coordinated through tsk tasks | Whether tsk records carry a full run without a separate script holding state | Tests passing, regressions after merge, tokens, share of output kept |
| Validate the judge first: before a run, record that the check passes the original and fails seeded broken code | Whether a record of judge validation is worth a new field or a decision record is enough | Seeded faults caught by reviewers and by the oracle |
| Retry and budget caps held as constraints, then as fields | Whether a cap in prose is obeyed, compared with a cap tsk refuses to pass | Attempts per task, runaway tasks, cost per task |
| An issue backlog run in the Next.js pattern on this repo's own open questions: read-only research agents write evidence documents, a counter-agent argues for keeping each item open, a human closes | Whether questions and linked documents serve as a close queue | Items closed, items reopened, human minutes per item |
| A process audit by a human from Dolt history alone after one of the runs above | Whether the ledger answers "who claimed, who reviewed, what was retried" without the transcripts | Questions the history could not answer |
| The ultimate test: rewrite a bounded system whose behaviour a test suite or a parity diff already fixes, with every unit claimed and closed through tsk | The mission objective itself | Same as Bun: duration, cost, regressions, share kept |

## Conclusion

The recruiting post's phrases are each true of one case and false as a general description. Hundreds of agents at once is documented, but the system-scale runs that kept their output used 16 to 64 agents against an oracle, while the largest agent count produced a browser with red CI. "Overnight" is not documented for an entire system; a weekend with two discarded runs and 11 days with a 60,000-test suite are. Hundreds of issues in a session is documented as agent research with a human closing each issue. The scale that matters is the strength of the check, not the number of agents.

For tsk, the evidence moves the question from "can the ledger hold many agents" to "can the ledger refuse work that has not passed its check". Every successful run made one step mechanical that tsk leaves to a person: deciding that a unit is done. The first experiments for M-TSK-SCALE should therefore measure claim contention and a small oracle-backed port before any attempt to rebuild a whole system.
