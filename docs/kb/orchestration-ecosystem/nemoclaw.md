# OpenShell contains the robot; tsk coordinates it

NVIDIA NemoClaw, as of October 2026, is an open-source (Apache 2.0) reference stack that installs NVIDIA OpenShell, a sandbox runtime, and runs a supported agent inside it, with onboarding, inference routing, network policy presets and per-host lifecycle commands. OpenClaw is its default agent, but no longer its only one: Hermes, LangChain Deep Agents Code and Pi (release candidate) sit beside it. NemoClaw is alpha at v0.0.139 (26 October 2026), while OpenShell has its own stable 0.1.x line at v0.1.6. In the frame of the earlier analyses of Dify, n8n, Dust, StackAI and Entire, the three components sort cleanly: **OpenShell is a deployment substrate**, NemoClaw is a substrate plus an agent distribution, and OpenClaw is an agent harness that tsk could integrate with. None of them is a competing coordination system. They contain and route an agent on one host; they hold no shared record of missions, tasks, decisions, questions, threads or actors, and nothing in them is synced over git. For an unsupervised coding robot, OpenShell alone is the stronger candidate: it supports Claude Code, a custom image and named volumes, and adds per-binary egress policy and credential injection that the Claude Code cloud baseline does not have. It has no scheduler, so tsk still needs an outside trigger, and its operator approval prompt for blocked egress halts an unattended run until a person answers. NemoClaw adds an OpenClaw-centred personal-assistant layer that a tsk robot does not need, at alpha stability and with manual recovery after a host reboot.

## NemoClaw wraps the most-starred agent in NVIDIA's sandbox

NVIDIA announced NemoClaw at GTC on 16 March 2026 under the title "NVIDIA Announces NemoClaw for the OpenClaw Community", as a one-step install of Nemotron models and the OpenShell runtime with added privacy and security controls ([SiliconANGLE, 16 Mar 2026](https://siliconangle.com/2026/03/16/nvidia-launches-nemoclaw-agent-toolkit-enhance-ai-agents/); [NVIDIA investor release](https://investor.nvidia.com/news/press-release-details/2026/NVIDIA-Announces-NemoClaw-for-the-OpenClaw-Community/default.aspx)). The notes took these launch details from coverage, not from the full text of the release. OpenShell shipped at the same event as part of the NVIDIA Agent Toolkit ([NemoClaw docs home](https://docs.nvidia.com/nemoclaw/home)). The current documentation describes NemoClaw as "an open source reference stack for running supported and qualified candidate AI agents more safely" inside OpenShell sandboxes, with "guided onboarding, managed inference, network policy, managed integrations, and lifecycle operations" ([NemoClaw docs home](https://docs.nvidia.com/nemoclaw/home)). The division of labour is explicit: NemoClaw owns the host CLI, onboarding, a "versioned blueprint" and the baseline policy; OpenShell owns "network namespace isolation, the CONNECT proxy, policy enforcement, inference routing, TLS termination, and structured platform logging"; the agent runtime owns "the agent loop, tools, skills" ([Enterprise readiness](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/enterprise-readiness.md)). NVIDIA also states that "OpenShell stays the sandbox and policy engine; nothing requires NemoClaw's blueprint or CLI" ([NemoClaw ecosystem](https://docs.nvidia.com/nemoclaw/latest/about/ecosystem.html)), which is the fact that makes OpenShell usable on its own.

The maturity of the two differs. The NemoClaw README says "NemoClaw is an alpha project" with best-effort support ([GitHub NVIDIA/NemoClaw](https://github.com/NVIDIA/NemoClaw)), and the release notes show **several releases a week**: v0.0.135 on 15 October, v0.0.137 on 20 October with Nemotron 3.5 Super VL as the new default hosted model, v0.0.139 on 26 October ([Release notes](https://docs.nvidia.com/nemoclaw/latest/about/release-notes.html)). No GA date exists; one blog guessed Q3 or Q4 2026, which is speculation ([nemovideo.com](https://www.nemovideo.com/pt-BR/blog/what-is-nemoclaw-ai-agents-video-teams)). OpenShell publishes dev, pre-release and stable builds, says "Tagged stable releases generally go out every week", and keeps stable interfaces backward-compatible across patch releases ([OpenShell support matrix](https://docs.nvidia.com/openshell/about/support-matrix.md)). On 28 October the repositories showed **22.9k stars for NemoClaw and 20.6k for OpenShell** ([NemoClaw repo](https://github.com/NVIDIA/NemoClaw); [OpenShell repo](https://github.com/NVIDIA/OpenShell)), read from rendered pages because the GitHub API was not available to the research session.

OpenClaw explains why NemoClaw exists. Formerly Clawdbot and then Moltbot, it is a self-hosted, always-on personal agent with a gateway, chat channels, skills from the ClawHub registry, heartbeats and Markdown memory files. It passed 250,000 stars on 3 March 2026 and reached about 380,000 by July, by third-party counts ([gradually.ai](https://www.gradually.ai/en/openclaw-statistics/)); its creator joined OpenAI in February and the project moved to a foundation ([Simon Willison](https://simonwillison.net/2026/Feb/15/openclaw/)). Its security record is poor. Koi Security found **341 malicious skills among 2,857** audited on ClawHub ([The Hacker News](https://thehackernews.com/2026/02/researchers-find-341-malicious-clawhub.html)), a secondary source counts over 1,184 by 1 March, and the same aggregators report exposed instances growing from about 1,000 to over 21,000 in one week of January, later over 135,000, plus CVE-2026-25253, a one-click RCE at CVSS 8.8 ([barrack.ai](https://blog.barrack.ai/openclaw-security-vulnerabilities-2026/)). The notes did not read the primary Censys or SecurityScorecard reports, so those counts carry their method and date caveats. Jensen Huang called OpenClaw the "operating system for personal AI" ([TechRadar](https://www.techradar.com/pro/this-is-as-big-of-a-deal-as-html-as-big-of-a-deal-as-linux-nvidia-nemoclaw-looks-to-make-openclaw-safer-and-more-effective-for-business-use)). The notes infer two motives for the wrapper: to make OpenClaw safe enough for business use, and to place NVIDIA hardware and NVIDIA Endpoints under it. Hacker News commenters made the second point at launch ("Trojan horse"), as relayed secondhand ([wikidocs.net](https://wikidocs.net/blog/@jaehong/9479/)). Futurum called the stack a deployment-trust layer, not a governance solution ([CIO](https://cio.com/article/4146545/nvidia-nemoclaw-promises-to-run-openclaw-agents-securely.html)), and NemoClaw has had a CVE of its own: CVE-2026-65105, an unauthenticated Ollama bound to `0.0.0.0:11434`, fixed in v0.0.35 on macOS and Linux and reported unfixed on WSL at the time; its date is not established ([aiweekly](https://aiweekly.co/node/10937)).

## OpenShell routes every packet through a supervisor and hides the keys

OpenShell's model is the part that bears on a tsk robot. A gateway is the control plane, and for each sandbox a compute driver creates a workload and a separate trusted supervisor. "In the current Linux backend, the workload uses one non-root identity and no Linux capabilities. Landlock limits filesystem access; seccomp user notification stages network operations" ([OpenShell architecture](https://docs.nvidia.com/openshell/about/architecture.md)). On Docker and Podman the "workload container has networking turned off", on Kubernetes a NetworkPolicy allows only the supervisor, and on a microVM the guest has no network device; the supervisor "checks requests against policy, supplies credentials, resolves DNS, opens approved connections", and identifies the calling executable from `/proc` ([OpenShell architecture](https://docs.nvidia.com/openshell/about/architecture.md)). Two consequences follow. Egress policy is **per binary, deny by default**, and "Agents never see real credentials; OpenShell adds them only to requests bound for approved endpoints" ([OpenShell architecture](https://docs.nvidia.com/openshell/about/architecture.md)). The system fails closed: "If the supervisor disconnects, the sandbox freezes the agent." Filesystem and process policy are fixed at creation, network policy reloads hot, policy is YAML under version control, and a "policy prover" that "uses formal verification" blocks auto-approval of an agent-proposed change that adds credentialed reach or cloud metadata access ([OpenShell overview](https://docs.nvidia.com/openshell/latest/index.html)). With no policy supplied, the working directory and `/tmp` are writable, system paths are read-only, and all outbound network access is denied; Docker and Podman reject a root image user, and Landlock ABI v3 needs Linux 6.2 or later ([OpenShell default policy](https://docs.nvidia.com/openshell/how-it-works/policies/default-policy.md)).

OpenShell runs on Linux, Apple Silicon macOS and WSL2 (experimental) with Docker 28.0+, Podman 5.x, Kubernetes 1.29+ through a Helm chart, or microVMs ([OpenShell support matrix](https://docs.nvidia.com/openshell/about/support-matrix.md); [runtimes](https://docs.nvidia.com/openshell/how-it-works/sandboxes/runtimes.md)). It names **Claude Code, OpenCode, Codex and GitHub Copilot CLI** as supported agents and accepts "the default Ubuntu workload or bring your own containerized runtime" ([OpenShell overview](https://docs.nvidia.com/openshell/latest/index.html)). Persistent storage is a labelled Docker or Podman named volume or `tmpfs` attached through driver config, for example `target: /sandbox/work`, with driver config "disabled by default" ([OpenShell runtimes](https://docs.nvidia.com/openshell/how-it-works/sandboxes/runtimes.md)). The gateway's own record of sandboxes sits in SQLite or an external database ([support matrix](https://docs.nvidia.com/openshell/about/support-matrix.md)); that is infrastructure state, not work state.

NemoClaw adds to this a host with a stated minimum of 4 vCPU, 8 GB RAM and 20 GB disk (16 GB and 40 GB recommended), Node.js 22.19+, and a sandbox image of about 2.4 GB compressed ([Prerequisites](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/get-started/prerequisites.md)). A GPU is needed only for local inference. Anthropic is "Tested" through a native Messages API adapter, with OpenAI, Gemini, OpenRouter, NVIDIA Endpoints and local Ollama, vLLM, llama.cpp and NIM beside it, and "The sandbox does not receive your raw OpenAI, Anthropic, Gemini, or NVIDIA API key" because inference goes through `inference.local` ([Inference options](https://docs.nvidia.com/nemoclaw/latest/inference/inference-options.html)). Its network policy is deny by default, and "OpenShell intercepts any request to an unlisted destination and prompts the operator to approve or deny it in real time through the TUI" ([NemoClaw network policies](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/network-policies.md)). "GitHub access (github.com, api.github.com) is not included in the baseline policy"; a `github` preset covers "GitHub API access or Git access" for OpenClaw and Hermes ([Integration policy examples](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/network-policy/integration-policy-examples.md)). Scheduling is OpenClaw's heartbeat, which wakes the agent every 30 minutes by default (one hour for Anthropic OAuth) to "review follow-ups and read HEARTBEAT.md" ([Configure agent heartbeats](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/configure-agents/configure-agent-heartbeats.md)), plus chat channels from Telegram to Microsoft Teams. Each host is managed on its own: "There is no cross-host management console", SSO is "Roadmap-only", and "Host Reboot Recovery Is Manual" ([Enterprise readiness](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/enterprise-readiness.md); [Deploy to a headless server](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/deployment/deploy-to-headless-server.md)). Both projects are free; the costs are the host, the tokens and NVIDIA hardware only for local models. There is no NVIDIA-hosted NemoClaw service ([Enterprise readiness](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/enterprise-readiness.md)).

## Three components, three roles, and none competes with the ledger

The earlier analysis tested each platform on one question: does it give an agent a Linux filesystem, network and arbitrary binaries for the length of a run. Dify, n8n, Dust and StackAI fell short of that in different ways and were better placed as callers of tsk; Entire did not host the agent at all and fitted as a capture-and-review layer beside the ledger. The NVIDIA stack passes the test, which puts it with the sandboxes of the earlier report (E2B, Daytona, Modal, Kubernetes Agent Sandbox), not with the builders. It differs from those sandboxes in being self-hosted and free, and in enforcing egress per executable rather than per sandbox.

| Component | Role relative to tsk | Fit for an unsupervised tsk robot | Main limit |
|---|---|---|---|
| OpenShell 0.1.6 | Deployment substrate | Good: Claude Code supported, custom image, named volume, per-binary egress, credential injection | No scheduler; blocked egress waits for an operator; self-hosted |
| NemoClaw 0.0.139 | Substrate plus agent distribution | Possible with friction: Claude Code is not one of its four agents | Alpha cadence, manual reboot recovery, one host per install, read-only host mounts |
| OpenClaw | Agent harness, a layer to integrate with | Poor as the robot itself: a personal assistant, not a coding harness | Malicious-skill and exposed-instance record |

The three rows rest on the documentation cited in the sections above and on the notes' classification. OpenClaw's sub-agents and its "declarative agents manifest" ([NemoClaw docs index](https://docs.nvidia.com/nemoclaw/latest/llms.txt)) are the nearest thing to multi-agent coordination in the stack, and they run inside one sandbox. NemoClaw's own multi-agent statement is that "Side-by-side sandboxes use distinct names, and each name maps to exactly one agent type", with "Known multi-instance issues" ([Enterprise readiness](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/enterprise-readiness.md)). OpenShell describes itself as a runtime "for executing fleets of autonomous AI agents in sandboxed environments" ([OpenShell overview](https://docs.nvidia.com/openshell/latest/index.html)), but "fleet" there means many sandboxes under one gateway, not agents that share a plan.

## An unsupervised robot fits OpenShell, given an outside clock

The tsk robot today is a Claude Code cloud session started by a routine, with a clone, `tsk`, `git` and `dolt`, a GitHub proxy that accepts only branch pushes, and continuation state in the ledger. On OpenShell the equivalent is a sandbox created from a custom image that holds `tsk`, `git` and `dolt` (the OCI image that the earlier report already recommended), Claude Code as the agent, a YAML policy that allows `github.com:443` for the binaries that reach the remote, a provider entry for the Anthropic key, and a labelled named volume for the clone and the ledger store path. The notes reach this design by inference; nobody has built it. What it gains over the cloud baseline is containment: the agent process never holds the GitHub token or the Anthropic key, and an exfiltration attempt to an unlisted host fails at the supervisor. What it loses is the clock. OpenShell has no cron, no webhook trigger and no run record, so a host cron, a GitHub Actions schedule or a Claude Code routine that calls the host must start each run. The notes also found **no documented run-duration cap and no idle stop**, which removes the ceilings that the earlier report listed for the hosted field, and also removes the cleanup that a ceiling forces.

Four points of friction are specific to tsk. First, egress is per binary, so the policy must name each executable that talks to GitHub. Under the 0.21.0 Dolt file remote, the ledger moves with plain `git fetch` and `git push` and "Dolt never starts git", so the entry that matters is `git`; this repo's ledger is still in the older `git-remote` layout, where Dolt drives the git remote, and the notes did not verify whether that traffic passes OpenShell's L7 checks. Running `tsk ledger migrate-transport` before a move narrows the policy to one binary. Second, the notes did not confirm whether NemoClaw's `github` preset grants `/usr/bin/git` or only the agent binary. Third, the local Dolt server of ADR 0018 listens on loopback; OpenShell mediates TCP opens through seccomp and lists loopback forwarding as a function, but whether a loopback connection needs a policy entry is unverified, and `TSK_DOLT_SERVER=off` is the fallback. Fourth, and most important for unattended work, a request to an unlisted destination raises an operator prompt in the `openshell term` TUI ([Monitor sandbox activity](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/monitoring/monitor-sandbox-activity.md)). A robot that reaches a new package mirror then stops until a person answers. For a tsk robot the policy has to be complete before the run, and a blocked request has to count as a failure that the run records in the ledger as an open question rather than a silent stall.

NemoClaw on top adds little for this case and some cost. Claude Code is not among its four agents, so the robot would run as Deep Agents Code or as Claude through OpenClaw, neither of which carries tsk's plugin hooks. "Every accepted host mount is read-only" ([Understand sandbox state](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/manage-sandboxes/state-and-backups/understand-sandbox-state.md)), so the clone must live in the sandbox's persistent volume, and `nemoclaw <name> destroy` "deletes the sandbox and its persistent state volume". "Network policy and inference auth are not enforced if a runtime starts outside the NemoClaw-managed entrypoint", and approvals reset to the baseline when a sandbox is recreated ([Enterprise readiness](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/enterprise-readiness.md)). A host cron that runs `nemoclaw <name> exec -- ...` is the likely trigger, but the notes did not verify that it works. Because tsk keeps its state in the remote ledger and rebuilds the store with `tsk ledger fetch`, losing a sandbox loses only unpushed local writes, which the `Stop` hook's background publish already keeps small; that property makes a tsk robot more tolerant of NemoClaw's manual recovery than an OpenClaw assistant whose memory lives only in the sandbox.

## NVIDIA's stack duplicates the heartbeat and lacks the ledger

The overlap with tsk is small and sits at the runtime edge. OpenClaw's heartbeat is a periodic wake-up, the job that a Claude Code routine does for a tsk robot. NemoClaw's per-session JSONL logs under `/sandbox/.openclaw/agents/main/sessions/` record assistant messages, tool calls, token usage and cost, with a `.trajectory.jsonl` for replay ([Monitor sandbox activity](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/monitoring/monitor-sandbox-activity.md)), which is closer to Entire's checkpoint than to anything tsk stores. OpenClaw's Markdown memory files hold "personality, user context, and behavioral configuration" ([Understand sandbox state](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/manage-sandboxes/state-and-backups/understand-sandbox-state.md)), and they resemble continuation state only in form: they belong to one sandbox on one host, and handover between agents means a manual state transfer. Audit export, SIEM integration and fleet disaster recovery are all "Manual or admin-only" ([Enterprise readiness](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/enterprise-readiness.md)).

| tsk function | NemoClaw, OpenShell, OpenClaw | Assessment |
|---|---|---|
| Scheduled start of a robot run | OpenClaw heartbeat (30 min default), chat channels | Partial duplicate, in-sandbox only; no cron or webhook |
| Session record | Per-session JSONL and trajectory files, OCSF logs from OpenShell | Duplicated at host level; not tied to commits or shared |
| Continuation state and hand-off between actors | Memory files per sandbox; manual state transfer | Absent as a shared object |
| Missions, objectives, constraints, tasks with claims | None | Absent |
| Decisions and open questions as records | None | Absent |
| Actors, robot identity, instances, thread bindings | Sandbox names; one agent type per name | Absent |
| State synced over git refs, mergeable between hosts | Gateway state in SQLite; nothing git-backed | Absent |
| Sandbox, per-binary egress, credential custody, inference routing | All present | NVIDIA has them; tsk does not |

The table follows the notes' synthesis of the pages cited in this report. The gap that matters is the same one the Entire comparison found: the claim. Two OpenShell sandboxes on two hosts have no way to see that the other has taken a task. tsk supplies that, and OpenShell supplies the boundary that tsk does not.

## Used together, OpenShell holds the process and tsk holds the plan

Three integrations are open, in rising order of coupling. The first is tsk inside an OpenShell sandbox as described above, with Claude Code and the tsk plugin unchanged; it needs only the image, the policy and a trigger. The second is tsk exposed to an OpenClaw or Deep Agents agent. An OpenClaw skill that wraps the `tsk` CLI is the cheapest route, and a tsk MCP server registered as a NemoClaw managed MCP server ([NemoClaw docs index](https://docs.nvidia.com/nemoclaw/latest/llms.txt)) is the more structured one; it is the same HTTP MCP front end that the earlier report recommended for Dify, n8n, Dust and StackAI, and that the Entire report proposed for Trail agents. The third uses OpenShell's policy prover and OCSF logs as evidence in the ledger: a run could record its policy version and blocked-egress events in its continuation entry, so the next actor sees why a run stopped. That last one is a design idea from this synthesis, not something either project documents.

The risks are concrete. NemoClaw is alpha with releases several days apart, and its blueprint and defaults move under a robot that runs unattended; pinning OpenShell's stable line and skipping NemoClaw avoids most of that. The approval prompt converts a missing policy entry into a stall, and the "Personal" tier that avoids prompts allows any host on ports 80 and 443, so that "An agent can send workspace data or sandbox-visible credentials to an arbitrary reachable service ... without an operator approval prompt" ([NemoClaw network policies](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/network-policies.md)); neither extreme suits an unsupervised robot. Publishing a tsk skill to ClawHub puts it in a registry with a record of malicious skills, although ClawHub now hashes skills and checks them against VirusTotal ([barrack.ai](https://blog.barrack.ai/openclaw-security-vulnerabilities-2026/)). Self-hosting moves the operations burden to the tsk user: reboot recovery, Landlock kernel requirements and host patching, all of which the Claude Code cloud baseline absorbs. The notes infer that NVIDIA's defaults steer inference to NVIDIA Endpoints and hardware; with Claude through the Anthropic adapter that pull has no effect on a tsk robot, but the defaults will need overriding at each onboarding. Finally, several facts are still untested: the `github` preset's binary list, Dolt's `git-remote` traffic through the L7 checks, loopback for the Dolt server, and the `nemoclaw exec` trigger.

### Dify's `openshell` backend is documented, but not shown to be NVIDIA's

The two sets of notes conflict on one point, and the earlier notes settle half of it. The NemoClaw notes say no source confirms an `openshell` backend in Dify. The earlier Dify notes cite Dify's self-hosting environment variable reference for `DIFY_AGENT_RUNTIME_BACKEND`, whose values are `local` (the bundled container), `e2b` (an E2B VM per sandbox) and `openshell`, glossed as "your own OpenShell gateway", together with `DIFY_AGENT_OPENSHELL_SANDBOX_IMAGE` (default `docker.io/library/dify-agent-runtime:latest`), `DIFY_AGENT_OPENSHELL_EGRESS_ALLOW` (a comma-separated `host:port` allow list, "When set, only the listed hosts are reachable, so include the Dify callback hosts") and `DIFY_AGENT_OPENSHELL_SHARED_MOUNT_PATH` (default `/mnt/dify-agent-shared`, where "Agents' persistent files are saved here when you click Apply") ([Dify Docs, Environment Variables](https://docs.dify.ai/en/self-host/deploy/configuration/environments)). So a Dify backend named `openshell` exists in the documentation as cited, and the NemoClaw note's statement is too strong. The Dify notes' summary also lists an OpenShell marketplace plugin, but their cited findings name only E2B and Daytona plugins, so that plugin is unsupported. Neither set of notes shows that the backend is NVIDIA's OpenShell. The cited lines do not name NVIDIA. The term "gateway" and the pairing of a custom image with an egress allow list match NVIDIA OpenShell's architecture, and Dify's agent sandbox also uses Landlock, but that is resemblance, not evidence, and Dify's documented sandbox sits behind a Squid egress proxy, a different design from OpenShell's per-binary supervisor ([Railway Dify template](https://railway.com/deploy/dify-v1-ai-app-studio)). The identity of Dify's `openshell` backend is **unconfirmed**; the Dify agent-backend source (`langgenius/dify-agent-backend`) is where to check. If it is NVIDIA's OpenShell, the earlier report's one viable Dify configuration for tsk, self-hosted Dify with the OpenShell backend, would rest on the same sandbox analysed here.

## Conclusion

NemoClaw changes the shape of this research. Every earlier platform offered either a runtime with a weak boundary or a scheduler with no runtime, and tsk filled the coordination gap in both. NVIDIA's stack is the first that offers a strong boundary with no coordination at all, and its boundary is the one thing tsk's robots lack in the Claude Code cloud: the robot can push without holding the token, and cannot reach a host the policy does not name. That makes OpenShell a complement to tsk, not an alternative to the ledger, and it suggests that tsk's portability work (one OCI image, an install script, an MCP front end, runs that can stop at any point and resume from the remote) also serves as the path to a self-hosted, contained robot fleet.

The cost of that path is the clock and the operator. A tsk robot on OpenShell needs an outside trigger and a complete egress policy written before the run, because the sandbox's answer to anything unplanned is to wait for a person, which is the opposite of an unsupervised robot. Before any move, three tests settle most of the open facts: a `git push` of `refs/heads/tsk/ledger` from inside an OpenShell sandbox under a per-binary policy, the same push under the older `git-remote` transport, and a host-cron trigger of a Claude Code run in the sandbox. NemoClaw itself is worth revisiting when it leaves alpha and if it adds Claude Code to its agents; until then, OpenShell alone is the layer to evaluate.
