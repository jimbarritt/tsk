A mission has an internal ID and a code, and `tsk mission mv`, `task mv`, `decision mv`, `question mv` and `ledger doc mv` rename and move (M-ADMIN-02 T-25, ADR 0026). The ledger is at layout 10.

- **Layout 10 adds `missions.code`.** `missions.id` stays the primary key and becomes the internal ID, which every other table names the mission by and which never changes. `code` is the mission ID a person types and sees. The first write on layout 9 adds the column after `id`, sets it to the `id` of every mission, adds the unique index `missions_code_unique`, and records version 10. Nothing else changes, so Dolt merges two clones that each upgrade, and a clone with unpushed changes merges with an upgraded origin. A mission made before the upgrade has its first ID as its internal ID. A mission made after has a random UUID. A `code` that is null reads as the `id`. A `tsk` older than 0.30.0 stops at a layout 10 ledger with `unsupported ledger version 10` and, from 0.18.0, updates itself.
- **A first design was dropped.** Keying every table by a new `uid` changed the primary key of the mission tables. A test with real Dolt showed that such a table does not merge: two clones that upgrade on their own, or a clone with an unpushed change meeting an upgraded origin, stop with `cannot merge because table missions has different primary keys in its common ancestor`.
- **`tsk mission mv <old> <new> [--dry-run]`** changes `code` and nothing else. Tasks, decisions, questions, blocks, parents and threads follow because they hold the internal ID. A clone that adds a task to the mission while another renames it merges with it. Each linked document whose path names the mission (`M-X.md`, `M-X-slug.md`, a directory `M-X`) is renamed, and its link follows. It refuses an unknown mission, a bad ID, an ID a mission has, the ID the mission has, and a document path that exists. It prints `mission <old> -> <new>`, one `doc` line for each document, and one `mentions` line for each record whose text names the old ID, which it does not change.
- **`tsk task mv`, `tsk decision mv` and `tsk question mv`** move a record to another mission, which gives it the next number there. A task takes the decisions that name it. A task with blocks is refused and the refusal names them. `--force` drops them. A decision is addressed by its place in `tsk decision list`, and its task link is cleared unless `--task` names a task of the target. Each prints one line per change.
- **`tsk ledger doc mv <from> <to>`** renames a document and updates the mission links to it.
- **A mission save removes** a task, a decision or a question that the mission no longer holds. It writes decisions before it removes a task.
- **`tsk mission list --json`** has a `uid` field: the internal ID.
- **`tsk ledger status`** after the upgrade shows the upgrade label, then the rows changed since origin as before.
- **Renumber lines** name the mission by its code.
- Tests: `cli/tests/conformance.rs` (a layout 9 ledger upgrades and keeps every record; two clones that upgrade on their own merge; a rename merges with a task and a question added to the old code on another clone; the five `mv` commands, their refusals and their lines; every older layout still upgrades) and unit tests in `cli/src/mission/mv.rs`.
- The plugin is 0.3.25 and requires tsk 0.30.0. The `tsk` skill lists the `mv` commands.
- Documents: ADR 0026, `docs/domain/ledger-layout.md` (layout 10, rename and move), the ubiquitous language (the mission code and internal ID), the user guide.
