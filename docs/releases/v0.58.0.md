A fresh cloud session asks for the robot on its first turn, and a later session start of the same session stays short.

- **`tsk thread next`.** Prints `bound:<thread-id>` and a line naming the thread and its mission for a bound session. Otherwise it prints the question the Stop hook asks, robot first: the registered robots and their threads, then the missions. It reads the local ledger store and never fetches. The nexus section that `setup-environment.sh --nexus` writes to `~/.claude/AGENTS.md` now says to run it in the first turn, once the ledger is fetched, so the robot is chosen before any other work and the Stop hook has nothing to ask.
- **A later session start of a bound session.** When a session ID already has a session start claim from another source (the context reload after `register_repo_root`, say), session start prints one line: the session is bound to the thread, and not to run `/tsk:resume-thread`. Before, it printed the full resume context a second time.
- **The plugin version warning.** It says that session start installed the new plugin, and that Claude Code loads plugins when its process starts, so a new session uses the new version.
- **Plugin 0.3.57:** the `tsk` skill lists `tsk thread next`.
- **Tests:** a conformance test for `tsk thread next` unbound and bound; unit tests for the earlier claim and the later start text.
