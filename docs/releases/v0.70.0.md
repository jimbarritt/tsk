The ledger state is outside the code repo (ADR 0035). Upgrade tsk: the next ledger command migrates your state and your nexus refs, with no step by hand.

- **One ledger home per repo.** The ledger store, the documents worktree and the file remote worktree are in `<state>/ledgers/<key>/`, beside a bare clone, `git/`, that tsk owns. `git worktree list` in the code repo lists none of them, `git for-each-ref` lists no ledger ref, and its object database gets no new ledger object. The home is named by the nexus entry id. Every clone and every linked code worktree of one repo on a machine share one home. A ledger in its repo has a home per clone, `_<clone-id>`. The code repo keeps `.git/tsk-clone-id`, `.git/tsk-repo-id` and `.git/tsk-ledger-home`.
- **New ref names in a nexus.** `refs/tsk/ledgers/<id>/ledger` and `refs/tsk/ledgers/<id>/docs`, or the `refs/heads/ledgers/<id>/...` form on a ledger that uses branches. They replace `ledgers/<id>` and `ledgers/<id>-docs`. A ledger in its repo keeps its refs.
- **The upgrade is automatic.** The next ledger command finds the state of 0.69.0 or earlier, migrates it, and renames the refs in the nexus. Unpushed Dolt commits, uncommitted rows, and uncommitted and unpushed documents all survive. Before it unregisters anything, the move compares every copied file with its source. Two processes can run it at once, and a run can repeat after an interruption.
- **What remains after the move.** The old directories are renamed to `<state>/repos/<clone-id>/legacy-leftovers/`, never deleted. tsk prints the path and the size once. Delete them once the ledger works. Git data that tsk fetched into the code repo stays there until git's own garbage collection drops them, two weeks after they are unreachable. tsk does not run `git gc` or `git prune` in your repo.
- **Two clones of one repo on one machine.** The first clone that upgrades migrates its copy. The next clone is merged into it, with the renumbering of ADR 0022, and its copy is kept in `<home>/preserved/<clone-id>/`. From then on the two clones share one lock, one Dolt server and one working set. An uncommitted change in one clone is visible in the other, and `tsk ledger discard` in either drops it.
- **A second machine** that upgrades later finds the refs moved and points its store at the new names. A machine that has not upgraded stops at its next ledger command, as the next item describes.
- **An older tsk stops, then updates itself.** The nexus entry of a moved ledger has a marker in `ledger_refs`: `<mode>-v2`, then a line that an older tsk reads as an unsupported ledger version. An older tsk stops before it does any ledger work, runs `tsk self-update` and repeats the command with the new tsk. With `TSK_AUTO_UPDATE=never`, and in the hook commands, it stops with an error that names the update. An older tsk cannot create a new empty ledger on the old names, because the server rejects the old name once the new refs exist. The manifest stays at layout 15, because the data did not change. The 16 in the marker is the generation of the ref layout, not a Dolt version.
- **A move that cannot finish.** A nexus that rejects a delete (a protected branch, a cloud proxy), an unreachable nexus and a lost lease keep the ledger working on the old names, with one note and no loss. tsk retries once an hour and at every `tsk ledger push`. During a move, a copy of the ledger is kept at `ledgers-backup/<id>/...`, and tsk deletes it when the new ref contains it.
- **`tsk nexus move-ledger`** copies through the bare clone of the ledger home of the clone, writes the new names and the marker, and renames the home of the ledger in the repo to the home of the ledger in the nexus.
- **New entries.** `tsk nexus register-repo`, `tsk ledger init --nexus` and `tsk nexus move-ledger` write `ledger_refs` with the marker. The mode is the one in force (`TSK_LEDGER_REFS`, then `.tsk/config.toml`), else `custom`, or `branches` in a Claude Code cloud session.
- **The guard** (ADR 0028) also covers the ledger homes (`<state>/ledgers/`, the bare clone included) and the new nexus ref names and their backups.
- **One version on one machine.** Run one version of tsk per machine. An older tsk that runs against a ledger in its repo after the upgrade starts a separate copy in `repos/<clone-id>`.
- **Tests.** `cli/tests/migrate_home.rs` builds a ledger, turns it into the layout of 0.69.0 (`cli/tests/common/legacy.rs`), and runs the new tsk against it. The cases cover both ref modes, both locations, an interruption at each step, two processes at once, a second clone, a rejected delete, a crash between delete and create, and a stray old documents ref. The test of a real older binary runs when `TSK_OLD_BIN` names one. CI fetches v0.69.0 (`ops/local/fetch-last-release.sh`) and sets `TSK_REQUIRE_OLD_BIN=1`, so a missing binary fails the run.
