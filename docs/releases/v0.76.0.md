This release shortens first-time setup of a repo with a local nexus and fixes problems in `tsk ledger init`.

- `tsk nexus init-local [<path>]` makes a bare git repo as a local nexus and attaches it. The default path is `~/.local/share/tsk/nexus.git`, and `XDG_DATA_HOME` changes it. The command lists its actions and prompts for confirmation before it runs them. `--yes` skips the prompt. It creates the folder above the nexus at mode 700 and runs `git init --bare --initial-branch=main`. It fails on a path that exists and is not an empty folder or an empty bare repo. It also fails while another nexus is attached, unless `--replace` is given. A replaced nexus keeps its ledgers. The command resolves `..` and symbolic links in the path before it compares the path with the attached nexus. Running it again for the attached nexus prints `already set up: <path> is the attached nexus` and exits 0. The command also sets the HEAD of an empty bare repo to `refs/heads/main`.
- `tsk ledger init` has `--territory-name`, which names a territory that the command creates. Without it the name is the territory id. An existing territory keeps its name.
- `tsk ledger init` has `--workflow main|pr`, which writes the push workflow to the nexus entry of the repo. On a terminal, without the option, the command prompts for the workflow when the entry has none. With no terminal, the workflow stays unset. `tsk ledger status` shows `workflow: <value>` or `workflow: not set` in the `Nexus` line of a clone with no ledger, and under `Ledger` once the ledger exists.
- `tsk ledger init` takes the mission prefix from the nexus entry of the repo when the entry has one and `--prefix` is not given.
- `tsk config ledger-refs <mode>` works with a nexus attached that has no entry for the repo and no ledger anywhere. It writes `.tsk/config.toml`, and `tsk ledger init --nexus` then writes the matching `ledger_refs` to the entry. `tsk config ledger-refs` with no argument prints the mode and a message that the nexus has no entry yet. The repo config sets the refs mode only. `tsk ledger init --nexus` or `--repo` sets where the ledger is stored, and the repo config never changes that. Afterwards the entry outranks the repo config.
- A commit to `nexus.json` has the robot as author and committer, and has the robot's signature, when `[attribution] identity` is `robot`. This covers `register-repo`, `add-territory`, `set-repo` and the other commands that edit `nexus.json`, and `tsk ledger init`. Before this release such a commit had the identity of the machine's git config or of the harness.
- With `[attribution] identity` set to `robot`, `tsk ledger init` registers the robot of the session in the new ledger and sets the mission prefix before its first commit. It reads the robot name from the `tsk-robot-name` file of the git directory, or from `GIT_AUTHOR_NAME` in a session that exports `TSK_SESSION`. With no name, or no signing set-up, it stops before it changes the nexus or the clone, and names `tsk actor register "<name>" --kind robot` and the `/tsk:construct-robot` skill. Earlier it left an entry in `nexus.json` and no ledger.
- Session start in a clone with no ledger writes the robot signing set-up before it prints the question, so `tsk ledger init` finds it.
- `tsk ledger init` writes the workflow to an existing nexus entry after the ledger is created and pushed. For a repo with no entry, the entry and its workflow are one commit that precedes the ledger.
- `tsk ledger status --porcelain` prints `workflow<TAB><value>` for a repo that has a nexus entry, with `-` when the entry has none.
- `tsk ledger not-used` records that a repo works without tsk. With a nexus attached that lists the repo, it writes the field `"tsk": "not-used"` to the nexus entry, and an older tsk ignores the field. Otherwise it writes `.git/tsk-not-used` in the common git directory, which every worktree of the clone shares. Session start then prints one line and makes no ledger store, and `tsk thread guard` blocks nothing. After the person chooses to work without tsk, the agent offers to remember the choice and runs the command only on acceptance. `tsk ledger not-used --forget` removes the field and the file. `tsk ledger status` mentions the mark, and `tsk ledger init` removes the file on success.
- Session start in a clone with no ledger gives the agent a question. With no nexus attached and no ledger on origin, the options are to create a local nexus, to attach a nexus by URL and to work without tsk. With a nexus attached that has no entry for the repo, the options are to initialise a ledger and to work without tsk, and the agent does not offer to register the repo. A cloud session gets no offer of a local nexus. A repo with a ledger choice in `.tsk/config.toml` or in `TSK_LEDGER_REFS` gets no question. `TSK_NEXUS_OFFER=off` switches the offer off, and an unattended start shows no question. A clone with no nexus and no ledger on origin no longer gets an empty local ledger at session start.
- `/tsk:init-ledger` names a `file://` nexus as "the local nexus" with its path and no longer states that the ledger is private. It offers to create a local nexus when none is attached, prompts for the push workflow, and prompts for a territory id and name when the nexus has no territory.
- The plugin is at 0.3.69. `tsk thread session-start` asks for the plugin update where an older plugin is installed.
