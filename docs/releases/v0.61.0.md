A new cloud session starts with fewer steps and no stale notes.

- **No clone of the nexus.** `tsk` fetches the nexus itself, into its own copies under the state directory, so the `add_repo` grant is all a cloud session needs. The session start text, the `Next` line of `tsk ledger status` and the nexus section that `setup-environment.sh --nexus` writes to `~/.claude/AGENTS.md` say not to clone it and not to run `register_repo_root` for it.
- **The failed nexus fetch is a step, not a warning.** In a cloud session, the fetch at session start fails until the agent attaches the nexus. The context now says so and gives the step, with no `Warning:` line.
- **No plugin version note in a cloud session.** A cloud session start installs the newer plugin itself, so the note named an out-of-date version by the time a skill loaded. A terminal session keeps it.
- **The session title in the resume output.** `tsk thread resume` prints `session_title`, with the `session_...` ID that `set_session_title` takes (the cloud variable holds `cse_...`) and the title. The resume skill uses it.
- **A version note on old pause entries.** A pause entry records the `tsk` version that wrote it. `tsk thread resume` (`version_note`) and session start say when that version is older than the one running, because a version or update step in the entry can be out of date.
- **`list_sessions` with `limit: 30`.** The robot choice in a cloud session asks for the 30 newest sessions. An open session older than those does not mark its robot as taken.
- **Plugin 0.3.60:** the resume skill reads `session_title` and reports `version_note`.
- **Tests:** unit tests for the version note and the nexus step; the session start test checks that a cloud session prints no plugin version note.
