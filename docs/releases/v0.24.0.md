Records are published by rule (ADR 0019). A record write never pushes, and `tsk thread resume`, `detach` and `thread set mission` stop pushing too. With a 330 ms network shim, `resume` takes 0.55 s where it took 1.18 s, `detach` 0.48 s where it took 1.10 s, and `thread set mission` 0.48 s where it took 1.11 s. The figures are medians of 7 runs on one machine.

- **Records are published at four points.** Thread start (the claim and the binding), thread pause and stop (the hand-off), the end of the session, and `tsk ledger push` when asked. Every publish carries every local change.
- **`thread resume`, `detach` and `set mission` write to the local ledger store and do not push.** Their stdout is the same as before. Each prints `note: saved in the local ledger store; it goes out with the next push (tsk thread start, pause or stop, or tsk ledger push)` on stderr when it changed something. The older note `the binding is saved locally; run tsk ledger push when origin is reachable` is gone, because nothing is pushed to fail.
- **A claim publishes at once.** `tsk thread start` pushes by itself. Setting a task or a mission to `in-progress` to take it is a record write, so the `start-thread` and `tsk` skills and `tsk guide import` tell the agent to run `tsk ledger push "Claim <mission> <task>"` straight after. Marking a task done, adding a task, recording a decision and answering a question are progress, and wait for the next publish.
- **A `SessionEnd` hook.** `plugin/hooks/session-end.sh` runs `tsk ledger push "End of session"` under an 8 s timeout (`TSK_SESSION_END_TIMEOUT_SECS`) when `tsk ledger status --local` shows unpushed work, and exits 0 whatever happens. It is registered for Claude Code (`SessionEnd`) and for GitHub Copilot CLI (`sessionEnd`). A container that is killed does not run it.
- **The `Stop` hook asks for a push when the ledger store holds unpushed changes.** `tsk thread guard` reads the local store, makes no network call, and blocks with a request for `tsk ledger push`. It says nothing for a clean store, and does not block again when the hook input has `stop_hook_active` set. The unbound-thread check comes first and is unchanged.
- **The event queue keeps pushing.** `tsk events append`, `append-batch` and `advance-watermark` hand a message to another process.
- **The skills and the guide state the rule.** `start-thread`, `pause-thread`, `resume-thread`, `detach-thread`, `switch-thread`, `stop-thread`, `tsk` and `tsk guide import`: write freely, publish at the four points.
- **The session start note about local changes** now reads "The next thread start, pause or stop pushes them with its own change, or run `tsk ledger push`."
- Tests: `cli/tests/thread.rs` (resume, detach and set mission leave origin unchanged and the next push publishes them; start publishes the claim for a second clone; pause and stop publish earlier writes; the Stop hook asks for a push only with unpushed work, honours `stop_hook_active` and needs no origin), `cli/tests/hooks.rs` (the `SessionEnd` script with a stand-in `tsk`, and the hook registration), and the conformance cases that relied on a pushing `resume`, `detach` or `set mission`.
- A clone with unpushed changes keeps them and does not merge origin when a thread command refreshes, as before, so after a `resume` it reads origin as last fetched until the next publish. `tsk ledger fetch` and the event queue reads refuse a store with unpushed changes. Run `tsk ledger push` first.
- The plugin is 0.3.14 and requires tsk 0.24.0. Update `tsk` and the plugin together. A `tsk` older than 0.24.0 works against the same ledger and pushes as it did.
