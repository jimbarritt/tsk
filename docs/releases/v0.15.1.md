A faster binary. The Dolt backend spawns fewer `dolt` processes.

Each `dolt sql` process costs about 80 ms. Before this release the Dolt backend ran one process per table, so a mission list read 11 tables in 11 processes. Measured on the tsk repo's own ledger, read-only:

| Command | 0.15.0 | 0.15.1 |
|---|---|---|
| `tsk mission list` | 0.81 s | 0.08 s |
| `tsk task list <id>` | 0.76 s | 0.08 s |
| `tsk mission list <id> --json` | 0.70 s | 0.07 s |
| `tsk decision list <id>`, `tsk question list` | 0.75 s | 0.08 s |
| `tsk thread guard` (the Stop hook) | 0.08 s | 0.09 s |

- The mission read runs every table query and the manifest check in one `dolt sql` process, and parses the results in order. It uses the batch only on a ledger at the current layout; any other layout, or a failed batch, takes the old query-by-query path, so results and errors are unchanged.
- `ledger status`, the refresh before a command, and `ledger push` batch their independent queries the same way. The push stages and counts in one process.
- A manifest check that finds the current layout is remembered for the rest of the process. Refresh, discard and push clear it.
- Writes still run in one transaction in one process. `task add` went from 1.08 s to 0.21 s on a scratch ledger, `thread start` from 4.3 s to 2.1 s, `ledger push` from 2.1 s to 1.1 s.
- Output is byte for byte the same as 0.15.0 over a scripted flow of about 110 commands, error cases and exit codes included.
- The conformance tests build each fixture once per test process and copy it. The whole workspace suite runs in under five minutes, from thirteen to sixteen.

Still slow: any command that fetches from origin. `tsk thread list` and `tsk ledger status` take 1.5 to 4 s on this ledger, because `dolt fetch` over a git remote reads objects one `git cat-file` process at a time. That is inside dolt.
