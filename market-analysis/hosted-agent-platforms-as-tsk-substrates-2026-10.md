# Agent builders schedule tsk; sandboxes host it

None of Dify, n8n, Dust or StackAI is a documented substrate for tsk in October 2026, and only one of them, StackAI, documents a shell sandbox that keeps files between steps of a run. The other three fall short in different ways: n8n Cloud has no shell node at all and the self-hosted Execute Command node is off by default since 2.0; the Dify Agent sandbox (beta, July 2026) runs commands but drops every file at the end of a published run and caps a run at one hour; Dust's Computer tool (June 2026) is a "temporary" sandbox whose language, shell and lifetime the docs do not state. The baseline, a Claude Code cloud session started by a routine, gives a fresh Ubuntu 24.04 VM with git, gh, rustc and cargo, a GitHub proxy and an hourly cron for no charge beyond the subscription, and the only missing piece for tsk is `dolt`. The four platforms sit in the workflow-automation and enterprise-knowledge segments of a market that Gartner places at the peak of inflated expectations and that consolidated through 2026: SAP invested in n8n at a **$5.2 billion** valuation, Asana bought StackAI for a reported **$75 million**, Flowise was archived and OpenAI retired Agent Builder. The substrates that run tsk unchanged are the ones that give a Linux filesystem, network and arbitrary binaries for the length of a run: Claude Code cloud, Managed Agents, GitHub Actions, Modal, E2B, Daytona, Fly Machines, Foundry hosted agents, and a self-hosted n8n or Dify with a custom image. The productive relation between tsk and the four builders is the inverse of hosting: tsk exposed as an HTTP MCP server, called from their schedulers. Three changes widen tsk's reach across the field: an OCI image with `tsk`, `git` and `dolt`, an install script that completes inside the five-minute snapshot window of the hosted clouds, and an MCP front end on the ledger and thread commands.

## The baseline gives tsk everything but dolt, at subscription cost

A Claude Code cloud session is "a fresh virtual machine (VM) running Ubuntu 24.04 on x86_64" with the repository cloned and common toolchains pre-installed, under approximate ceilings of **4 vCPUs, 16 GB of RAM and 30 GB of disk** ([Cloud environments](https://code.claude.com/docs/en/cloud-environments)). The pre-installed set includes Python, Node, Go, Java, "Rust: rustc and cargo", Docker, PostgreSQL 16, Redis 7 and "git, gh, jq, yq, ripgrep, tmux", and anything else must come from a setup script, because "Replacing the base image entirely isn't supported yet" ([Cloud environments](https://code.claude.com/docs/en/cloud-environments)). The session "counts toward your plan's usage limits alongside the rest of your Claude and Claude Code usage, and there's no separate charge for the cloud VM" ([Claude Code docs: cloud](https://code.claude.com/docs/en/claude-code-on-the-web)). Plans start at Pro ($17 a month annual, $20 monthly) and Max from $100 a month, with Claude Code "included in all paid plans" and limits that "reset on a rolling 5-hour window" plus weekly caps ([claude.com/pricing](https://claude.com/pricing)).

Three documented constraints shape a tsk bootstrap on this substrate. First, the setup window: when a setup script finishes "within roughly five minutes, Anthropic snapshots the filesystem and reuses that snapshot as the starting point for later sessions", the cache expires after roughly seven days, and a SessionStart command hook is cancelled "after 600 seconds unless you set timeout" ([Cloud environments](https://code.claude.com/docs/en/cloud-environments)). The cached snapshot is where a `dolt` install belongs. Second, the network: the default Trusted level allows package registries and GitHub, and the allowlist includes github.com and objects.githubusercontent.com, so a `dolt` release download is reachable at network level ([Cloud environments, Default allowed domains](https://code.claude.com/docs/en/cloud-environments#default-allowed-domains)). The GitHub proxy, though, returns 403 for "a source archive you fetch over a github.com/{owner}/{repo}/archive/ or codeload.github.com URL" of a repository not attached to the session, "even a public one" ([Cloud environments, GitHub proxy](https://code.claude.com/docs/en/cloud-environments#github-proxy)). Whether a release asset of an unattached repository such as dolthub/dolt passes is not documented, and the notes flag this as the one thing to test. Third, the push policy: the proxy "rejects branch deletions and pushes of anything other than a branch, such as a tag" ([Cloud environments, GitHub proxy](https://code.claude.com/docs/en/cloud-environments#github-proxy)). This is the documented platform constraint behind the repo's choice of `refs/heads/tsk/*` on cloud sessions, so the repo's ADR 0016 rests on a stated rule, not a transient bug.

Routines, now "scheduled tasks" in the docs, are "a saved Claude Code configuration: a prompt, one or more repositories, and a set of connectors, packaged once and run automatically", triggered by a cron schedule, an HTTP POST with a bearer token, or a GitHub event, and "in research preview" ([Routines](https://code.claude.com/docs/en/routines)). Each run is a fresh session: "Claude Code doesn't reuse sessions across events, so two PR updates produce two independent sessions", cron expressions "that run more often than once per hour are rejected", and the hourly caps are **100 scheduled runs per account, 30 API fires per task and 100 API fires per account**, with no overage ([Routines](https://code.claude.com/docs/en/routines)). Runs begin in auto mode, where "a classifier model allows or blocks actions", and "Claude pushes its work to a branch prefixed with claude/ unless your prompt directs it to push to another branch" ([Routines](https://code.claude.com/docs/en/routines)). A lapsed GitHub connection makes the task skip runs "for up to 72 hours" ([Routines](https://code.claude.com/docs/en/routines)). Idle sessions pause "after a few minutes without activity", a paused VM "can later be reclaimed", and reopening a reclaimed session loses "background work that was still running or pending", including shell commands and session-scoped scheduled tasks ([Claude Code docs: cloud, Environment expired](https://code.claude.com/docs/en/claude-code-on-the-web#environment-expired)). The docs publish no numeric idle threshold, maximum session length or concurrent-session cap, and no token figure per run, so the subscription cost per tsk run cannot be quoted from vendor pages.

The API-side twin, Managed Agents, is the one baseline with a price per hour. It is "a hosted agent harness that runs the agent loop, with sessions in an Anthropic-managed cloud sandbox or a self-hosted sandbox on your own infrastructure", in beta and "enabled by default for all API accounts" ([Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview)). Its cloud sandbox is smaller than the cloud session, "Up to 8 GB" memory and "Up to 10 GB" disk, Ubuntu 24.04 with "Rust: Stable toolchain (rustup), cargo" and `git` ([Cloud sandbox reference](https://platform.claude.com/docs/en/managed-agents/cloud-sandboxes-reference)). Runtime is "$0.08 USD per session-hour", accrued "only while the session's status is running", and the vendor's worked example of a one-hour Opus 5.5 coding session with 50,000 input and 15,000 output tokens comes to **$0.58** ([Claude Platform pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Three such runs a day is about $1.74 a day, or about $52 a month, by arithmetic on those rates rather than a vendor quote. Scheduled deployments take a POSIX cron with a timezone at minute granularity, apply "jitter of up to 15 percent of the interval between runs" capped at 9 minutes, allow "1,000 scheduled deployments" per organisation and cap each run's spend with a `budget` ([Scheduled deployments](https://platform.claude.com/docs/en/managed-agents/scheduled-deployments)). The self-hosted variant runs "a program that you run, called a worker" that carries out bash and file tool calls on your machines, at the cost of giving up the pre-installed runtimes and the `github_repository` session resource ([Choosing an agent environment](https://platform.claude.com/docs/en/managed-agents/choosing-an-environment)). One restriction applies to any agent built on the SDK rather than inside Claude Code: "Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products", so an SDK-driven tsk agent pays API rates ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)).

## The market consolidated around four segments, and the builders sit in the two without a shell

Analysts and vendors describe four segments in 2026: workflow automation with AI nodes (n8n, Zapier, Gumloop, Lindy), enterprise knowledge and work agents (Dust, StackAI, Copilot Studio, and Dify in part), coding agents with their clouds (Claude Code, Codex, Copilot, Cursor, Devin, Jules), and agent infrastructure (sandboxes, orchestration runtimes, protocols). Gartner's April 2026 Hype Cycle places agent development platforms at the Peak of Inflated Expectations and says "the market has not settled on dominant frameworks, protocols, or deployment patterns", with extra risk for platforms "that lock teams into one model provider, one cloud, one framework, or one integration protocol" ([xpander.ai summary of the Gartner Hype Cycle](https://xpander.ai/blog/gartner-hype-cycle-for-agentic-ai-what-it-means-for-ai-agent-development-platforms)). Gartner's July 2026 headline puts "$234 Billion in Enterprise Application Software Spend" at risk from agentic AI ([Gartner press release, 1 July 2026](https://www.gartner.com/en/newsroom/press-releases/2026-07-01-gartner-says-us-dollars-234-billion-in-enterprise-application-software-spend-is-at-risk-from-agentic-artificial-intelligence)); the notes record that the page returned 403 on fetch and the wording comes from the search index, and no Gartner primary text was read. Market-size figures differ by an order of magnitude with the definition: secondary roundups of Gartner give "AI agents and assistants" software at about **$29.2 billion in 2026**, up 77% from $16.5 billion, and "agent builder platforms at $5.0 billion in 2026", against $201.9 billion for agentic capabilities embedded across enterprise software ([Software Strategies roundup](https://softwarestrategiesblog.com/2026/02/26/roundup-of-agentic-ai-forecasts-and-market-estimates-2026/); [Deployed Labs](https://www.deployedlabs.com/blog/ai-agent-market-size-2026-data)). Menlo Ventures' December 2025 report, the latest enterprise survey the notes found, sizes enterprise generative AI spend at $37 billion in 2025, puts coding at "more than half of departmental AI spend at $4 billion", and estimates Anthropic at 54% of coding LLM usage "driven in large part by the popularity of Claude Code" ([Menlo Ventures report](https://menlovc.com/perspective/2025-the-state-of-generative-ai-in-the-enterprise/)).

Consolidation ran in two directions during 2026. Incumbents absorbed workflow tools: SAP's strategic investment on 12 May 2026 "values n8n at $5.2bn, more than double our valuation from less than a year ago" and embeds n8n "natively inside SAP's Joule Studio" ([n8n blog, SAP](https://blog.n8n.io/n8n-sap/)); the amount is not stated by n8n, and aggregators disagree (more than EUR 60 million per Wikipedia and Sacra, $70 million per Multiples.vc, $750 million per CB Insights), so the report carries the valuation and not the cheque ([Sacra](https://sacra.com/c/n8n/); [Multiples.vc](https://multiples.vc/private-comps/n8n); [CB Insights](https://www.cbinsights.com/company/n8nio/financials)). Asana acquired StackAI on 28 May 2026 for **$75 million** per TechCrunch, with Asana's own release silent on price ([TechCrunch, 28 May 2026](https://techcrunch.com/2026/05/28/asana-acquires-no-code-agent-builder-stack-ai/); [Asana press release via Nasdaq](https://www.nasdaq.com/press-release/asana-acquires-stackai-adding-cross-system-execution-human-agent-teams-2026-05-28)). Model vendors moved down into the runtime: Managed Agents launched in April 2026, Microsoft's Foundry hosted agents went generally available on 2 June 2026 accepting "a container-based agent built with the Microsoft Agent Framework or any third-party SDK" ([Azure update AZ563596](https://mc.merill.net/message/AZ563596)). The standalone builder layer between them shrank: "Flowise has been archived" on 13 August 2026 ([github.com/FlowiseAI/Flowise](https://github.com/FlowiseAI/Flowise)), and OpenAI's AgentKit page now states Agent Builder retires on 30 November 2026 ([OpenAI: Introducing AgentKit](https://openai.com/index/introducing-agentkit/)). Dify, the smallest of the four by capital, raised a **$30 million** Series Pre-A in March 2026 led by HSG, at a $180 million valuation per Business Wire that Dify's own post does not state ([Business Wire, 9 March 2026](https://www.businesswire.com/news/home/20260309511426/en/Dify-Raises-$30-million-Series-Pre-A-to-Power-Enterprise-Grade-Agentic-Workflows); [Dify blog, funding post](https://dify.ai/blog/dify-raises-30m-tomorrow-s-organizations-will-be-built-by-people-and-agents)). Dust raised a **$40 million** Series B on 18 May 2026 led by Abstract and Sequoia with Snowflake and Datadog, for more than $60 million in total, with ARR above $20 million per Sifted via Maddyness ([Tech.eu](https://tech.eu/2026/05/18/dust-raises-40m-series-b-to-build-the-multiplayer-operating-system-for-enterprise-ai/); [Maddyness](https://www.maddyness.com/2026/05/18/ia-dust-leve-40-millions-de-dollars-pour-accelerer-sa-croissance-aux-etats-unis/)).

Where each of the four sits follows from what it sells. n8n sells workflow automation to enterprises through SAP and Deutsche Telekom, claims "1.7 million monthly active builders" and "more than 1,400 enterprise customers" ([n8n blog, SAP](https://blog.n8n.io/n8n-sap/)), and a Series C press item's "more than 3,000 enterprise clients" conflicts with that ([technews180](https://technews180.com/funding-news/berlins-n8n-secures-180m-series-c-led-by-accel/)). Dify sells an agentic-workflow studio with a Marketplace, "Runs on more than 1.4 million machines" and names Maersk and ETS as customers ([Dify blog, funding post](https://dify.ai/blog/dify-raises-30m-tomorrow-s-organizations-will-be-built-by-people-and-agents)). Dust sells "multiplayer AI" to business teams, with 58 customer stories dominated by support, sales and company-wide adoption ([Customers](https://dust.tt/customers)). StackAI sells governed back-office automation to finance, healthcare, defence and legal, now as "the bridge" for Asana's AI Teammates ([Asana press release via Nasdaq](https://www.nasdaq.com/press-release/asana-acquires-stackai-adding-cross-system-execution-human-agent-teams-2026-05-28)). Their scheduling is a trigger node, their code execution is a per-step sandbox, and their persistence is the platform's own store. Against the coding-agent clouds they lack the long-running shell and repository; against raw sandboxes they add orchestration, connectors and a UI. The coding-agent clouds, by contrast, converged on one shape, "a saved prompt, a repository, a cron or event trigger, a fresh sandbox per run, a branch push, and a review queue", which is the category tsk's agents already occupy on Claude Code.

## Platform by platform: one documented shell, three gaps

The table condenses the substrate test. "Shell" means a documented way to run an arbitrary native binary; "files" means a filesystem that lasts at least one run; "cron" means an unattended scheduled start; "ceiling" is the documented run-duration cap.

|---|---|---|---|---|---|---|
| Claude Code cloud + routine (baseline) | Yes, full VM | Yes, for the VM's life | git, gh, proxy to GitHub; branch-only pushes | Hourly minimum | None published; "a few minutes" idle pause | Included in Pro/Max/Team |
| Managed Agents | Yes, 8 GB sandbox or your own worker | Yes, for the session | git present; unrestricted networking by default via API | Per-minute cron with jitter | Not published | $0.08 per running hour plus tokens |
| Dify | Only the Dify Agent beta sandbox (self-host); Code node has none | No in published runs; yes with OpenShell shared mount | Public URLs through a proxy; git presence undocumented | Yes, one schedule trigger per workflow | 3,600 s default, raisable self-hosted; cloud not published | Professional $590 a year, annual toggle |
| n8n | Self-hosted only, Execute Command off by default; Cloud has none | Self-hosted volume yes; Cloud ephemeral | Git node and Execute Command reach the network; no egress policy documented | Yes, durable scheduler since 2.45 | Cloud 5 to 40 min; self-hosted none by default | Starter EUR 20 a month annual; Community free |

### Dify: a shell arrived in July 2026, but a published run keeps nothing

Dify's classic Code node "runs in an isolated sandbox that blocks file system access, outbound network requests, and system commands", in Python or JavaScript only ([Dify Docs, Code node](https://docs.dify.ai/en/guides/workflow/node/code)). The change is the Dify Agent, experimental in 1.16.0-rc1 on 9 July 2026 and beta in 1.16.0 on 17 July 2026, with its home directory "protected with Landlock" ([GitHub, langgenius/dify releases](https://github.com/langgenius/dify/releases)). The agent "works inside its own sandbox, where it runs commands and handles files as it goes", can "install and run command-line tools on its own inside the sandbox", and reaches public URLs because "The sandbox's internet access goes through a proxy that blocks private-network addresses by design" ([Dify Docs, Build an Agent](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/build)). Two rules break the tsk model. Persistence: "In published runs, whatever the agent adds is always temporary, so nothing that happens in a run changes the agent itself", so a clone made in a scheduled run is gone when it ends ([Dify Docs, Build an Agent](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/build)). Duration: "A run stops after 1 hour by default, and the unfinished reply is discarded", and "Each run is capped at 500 model requests" ([Dify Docs, Build an Agent](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/build)). Dify also states that "the Agent runtime is not intended to provide a hardened security boundary between mutually untrusted users or workloads" ([Dify Docs, Build an Agent](https://docs.dify.ai/en/self-host/use-dify/build/new-agent/build)). No page lists the binaries in the `dify-agent-runtime` image, so whether `git` is present is unknown, and no page says in so many words that a downloaded native binary runs, although "command-line tools" reads that way.

Three runtime backends exist on self-hosted installs. `local` is the bundled container. `e2b` gives an E2B VM per sandbox with `DIFY_AGENT_E2B_ACTIVE_TIMEOUT_SECONDS` whose "Ceiling is 3600; higher values are rejected", which rules out a long session there ([Dify Docs, Environment Variables](https://docs.dify.ai/en/self-host/deploy/configuration/environments)). `openshell` is the one route where the operator controls the image (`DIFY_AGENT_OPENSHELL_SANDBOX_IMAGE`), an egress allow list of `host:port` entries, and a shared mount at `/mnt/dify-agent-shared` where "Agents' persistent files are saved here when you click Apply" ([Dify Docs, Environment Variables](https://docs.dify.ai/en/self-host/deploy/configuration/environments)). That is the only configuration in which `tsk`, `git` and `dolt` can be pre-installed on Dify, and it means self-hosting the API, workers, agent backend, sandbox gateway and a Squid proxy on a kernel with Landlock (5.13 or later), tracking releases every two to six weeks with breaking changes such as 1.18.0's agent run protocol ([GitHub, langgenius/dify releases](https://github.com/langgenius/dify/releases)). Triggers are mature by comparison: since v1.10.0 a Start node can be a Schedule trigger with a five-field cron, a Webhook trigger with a unique URL, or a Plugin trigger fed by GitHub events ([Dify blog, Introducing Trigger](https://dify.ai/blog/introducing-trigger)), with one schedule trigger per workflow ([Dify Docs, Schedule Trigger](https://docs.dify.ai/en/cloud/use-dify/nodes/trigger/schedule-trigger)). One self-hosted report of a `*/10 * * * *` schedule that started firing every two minutes after a few days is a single unconfirmed issue ([GitHub issue #41214](https://github.com/langgenius/dify/issues/41214)). Cloud pricing as read on 27 October 2026, with the page's toggle on annual, is Sandbox free with 3,000 trigger events, **Professional $590 a year** with 20,000 trigger events a month, and **Team $1,590 a year** with unlimited events; monthly prices were not captured ([Dify pricing](https://dify.ai/pricing)). The cloud run-duration ceiling and which agent backend Dify Cloud uses are not published. The licence is Apache 2.0 with a prohibition on operating a multi-tenant service without written authorisation ([GitHub, dify LICENSE](https://github.com/langgenius/dify/blob/main/LICENSE)). No published account of Dify as an agent that clones, edits and pushes a repository was found three months after the shell shipped; the community material is RAG chatbots, support automation and GitHub-events-to-Slack ([Dify blog, Introducing Trigger](https://dify.ai/blog/introducing-trigger)).

### n8n: the shell exists only self-hosted, and 2.0 turned it off

"The Execute Command node runs shell commands on the host machine that runs n8n", it "isn't available on n8n Cloud", and it is "disabled by default from n8n 2.0" ([Execute Command, docs.n8n.io](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executecommand/)). Re-enabling means setting `NODES_EXCLUDE` to `"[]"`, since the default excludes `executeCommand` and `localFileTrigger` ([Nodes environment variables, docs.n8n.io](https://docs.n8n.io/hosting/configuration/environment-variables/nodes/)). The command runs inside the n8n container, which is Alpine-based with "the `apk` package manager" removed, so `tsk`, `git` and `dolt` must be baked into a custom image that first restores `apk` ([Execute Command, docs.n8n.io](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executecommand/)). Files persist on self-hosted through the `/home/node/.n8n` volume ([Docker installation, docs.n8n.io](https://docs.n8n.io/hosting/installation/docker/)); on Cloud the file node "can only access paths under `/home/node/`" and files "may not survive later executions, restarts, or redeploys" ([Read/Write Files from Disk, docs.n8n.io](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.readwritefile/)). Cloud instances are small in any case: Starter gets "640MiB RAM, 10 millicore CPU burstable" ([Cloud data management, docs.n8n.io](https://docs.n8n.io/manage-cloud/cloud-data-management/)). The Cloud pricing page caps a Starter execution at **5 minutes** and a Pro execution at **40 minutes**, with Pro's concurrency given as 20 in the table and up to 50 in the plan text, a conflict on n8n's own page ([Pricing, n8n.io](https://n8n.io/pricing/)). Self-hosted `EXECUTIONS_TIMEOUT` defaults to `-1` and `EXECUTIONS_TIMEOUT_MAX` to 3600 s ([Executions environment variables, docs.n8n.io](https://docs.n8n.io/hosting/configuration/environment-variables/executions/)). In queue mode each worker has its own filesystem and "n8n doesn't support queue mode with binary data storage in filesystem", so a tsk host would be a single regular-mode instance ([Queue mode, docs.n8n.io](https://docs.n8n.io/hosting/scaling/queue-mode/)). A Git node with Clone, Fetch, Pull and Push against a local repository path exists, with bare repositories blocked by default since 2.0 ([Git node, docs.n8n.io](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.git/); [v2.0 breaking changes, docs.n8n.io](https://docs.n8n.io/2-0-breaking-changes/)). No n8n page states an egress policy for Cloud or self-hosted.

Scheduling is n8n's strength: the Schedule Trigger takes intervals or cron, and from 2.45 on 20 October 2026 "Schedule Trigger nodes now run on the durable scheduler by default", with misfire handling ([Changelog, docs.n8n.io](https://docs.n8n.io/changelog)). The MCP Server Trigger makes "n8n act as a Model Context Protocol (MCP) server" over SSE or streamable HTTP ([MCP Server Trigger, docs.n8n.io](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger/)). The public API overview documents no "run this workflow" endpoint; the notes read that from the overview and a mirror rather than the full OpenAPI listing, so a webhook is the documented API route ([API, docs.n8n.io](https://docs.n8n.io/api/)). Cost for a few runs a day is the licence and the machine: Starter **EUR 20 a month** annual for 2,500 executions, Pro EUR 50, Business self-hosted EUR 667 a month ([Pricing, n8n.io](https://n8n.io/pricing/)); the Community Edition under the Sustainable Use License allows use "for internal business purposes" at no charge ([LICENSE.md, n8n-io/n8n](https://github.com/n8n-io/n8n/blob/master/LICENSE.md)); a third-party estimate puts an 8 GB Hetzner host with managed PostgreSQL at about $24 a month ([openhosst.com, 2026](https://openhosst.com/blog/n8n-self-hosted-pricing)). The published community pattern is the reverse of hosting. NetworkChuck's guide states "n8n uses the SSH node to remotely execute Claude Code commands on your server" ([theNetworkChuck/n8n-claude-code-guide](https://github.com/theNetworkChuck/n8n-claude-code-guide)); Jonathan Mitchell's August 2026 pattern is "Claude Code does the actual code work. n8n handles everything around it", with the note "It's not a coding environment" ([jonathansblog.co.uk](https://jonathansblog.co.uk/claude-code-and-n8n-automating-your-development-workflow)); and the one community node that runs Claude Code in Docker needed the Docker socket, a custom image and `user: root`, which broke one user's data volume ([n8n community forum](https://community.n8n.io/t/claude-code-integration-for-n8n/244183)). Direction confirms the reading: n8n Agents (preview, 25 September 2026) are n8n-native objects with n8n nodes as tools, billed one turn per execution ([Introducing n8n Agents, blog.n8n.io](https://blog.n8n.io/introducing-n8n-agents/)), and the 2.0 security changes (Execute Command off, environment access blocked in Code nodes, file access restricted) move away from n8n as a general execution host. Two authenticated RCE flaws in January 2026 and 321 instances found accepting leaked API tokens in August 2026 are the security record a self-hoster takes on ([The Hacker News, January 2026](https://thehackernews.com/2026/01/two-high-severity-n8n-flaws-allow.html); [The Hacker News, August 2026](https://thehackernews.com/2026/08/leaked-n8n-api-tokens-exposed-live.html)).

### Dust: a sandbox with no documented shell, built for the opposite direction

Dust's Computer, launched 24 June 2026, is "a safe, temporary workspace where it can run code" that returns "finished artifacts to the conversation"; the page names no programming language and no shell beyond the `dsbx` helper, whose one documented command lists variable names and approved domains ([Computer](https://docs.dust.tt/docs/user-documentation/agents/tools/computer.md)). "Computer does not have open internet access by default": only admin-trusted domains, exact or wildcard, are reachable, and `DSEC_*` secrets reach Computer as placeholders that "Dust substitutes the real secret on the way out" of an approved HTTPS request ([Computer admin setup](https://docs.dust.tt/docs/user-documentation/admins/tools-management/computer-admin-setup.md)). Nothing documents installing binaries, running `git`, non-HTTPS egress, CPU, memory, time limits, or whether files survive from one message to the next in a conversation; both Computer pages were read in full. The documented ways to run your own code are a remote MCP server on a public URL ([Adding an MCP server](https://docs.dust.tt/docs/user-documentation/admins/tools-management/adding-an-mcp-server.md)) and a client-side MCP server in preview where "These tools execute in your client's environment", with a heartbeat every five minutes, an SSE request stream, OAuth personal access tokens only and conversation scope ([Client Side MCP Server](https://docs.dust.tt/docs/user-documentation/developers/client-side-mcp-server.md)).

Triggers are rich and metered. Schedules are written in plain language and "A Large Language Model generates the underlying schedule" ([Schedules](https://docs.dust.tt/docs/user-documentation/agents/triggers/schedules.md)); webhook triggers from GitHub, Jira, Linear, Zendesk, Fathom or a custom source run "at most 42 times per 24 hours" by default, and over the limit requests "are dropped, not queued or replayed" ([Rate limiting](https://docs.dust.tt/docs/user-documentation/agents/triggers/webhooks/rate-limiting.md)); wake-ups let an agent schedule itself, capped at 32 runs per schedule and one per conversation ([Wake-ups](https://docs.dust.tt/docs/user-documentation/agents/tools/wake-ups.md)); and the API creates a conversation with a mention ([Create a new conversation](https://docs.dust.tt/api-reference/conversations/create-a-new-conversation.md)). The custom webhook endpoint is documented as a "Skeleton endpoint that verifies workspace and webhook source and logs receipt", which the notes flag as something to confirm in a workspace before relying on it ([Receive external webhook](https://docs.dust.tt/api-reference/triggers/receive-external-webhook-to-trigger-flows.md)). Every unattended run is "programmatic usage" with "no free credit baseline", drawn from a workspace pool at **$0.01 a credit** on Business, where PAYG is not available ([Credit management](https://docs.dust.tt/docs/user-documentation/admins/usage-seats-and-credits/credit-management.md); [Pricing](https://dust.tt/pricing)). Seats cost **EUR 24 a month** on Pro billed yearly with 8,000 credits, EUR 120 on Max with 40,000, with Business capped at 100 people, 3 connectors and 5 remote MCP servers ([Pricing](https://dust.tt/pricing)). An external MCP call costs 3 action credits plus token credits, so a run with 50 calls is on the order of a few dollars by the notes' arithmetic; token credit rates per model are not published.

Dust positions itself away from coding on purpose. Its March 2026 post places Claude Code agents with "Developers writing, debugging, and reviewing code" and Dust with "business teams" automating Slack, Notion and CRM workflows ([Dust blog](https://dust.tt/blog/claude-code-agents)); its CLI's `skill:init` scaffolds a `SKILL.md` "so a local coding agent (such as Claude Code) can call Dust agents through the CLI" ([Dust CLI](https://docs.dust.tt/docs/developer-platform/dust-cli/dust-cli.md)); and Dust is itself a remote MCP server at `https://dust.tt/mcp` for conversations, Pod tasks and search ([Dust MCP Server](https://docs.dust.tt/docs/user-documentation/agents/integrations/dust-mcp-server.md)). The GitHub connector is "read-only" with default-branch code "Refreshed every 8 hours" ([GitHub connection](https://docs.dust.tt/docs/github)); the separate GitHub tool can "Search, update, comment, create pull requests and issues" as the `dust-agent` bot or the invoking user ([GitHub tool](https://docs.dust.tt/docs/user-documentation/agents/tools/github.md)), but its "Available Tools" section was empty on read, so whether it commits files is unconfirmed. Dust is SaaS in US and EU regions with "single-tenant deployment" on Enterprise ([Pricing](https://dust.tt/pricing)); the claim that there is "no supported self-hosting path" and that the repository is MIT-licensed comes from a competitor page, and the LICENSE file could not be read through the research sandbox's proxy, so both are unverified ([Onyx alternatives page](https://onyx.app/alternatives/dust)). Models span Claude 4.5 Haiku to Opus 5.5 and a gated "Claude Fable 5", with no statement of whether Anthropic, Bedrock or Vertex is the route ([Model access tiers](https://docs.dust.tt/docs/user-documentation/admins/usage-seats-and-credits/model-access-tiers.md)).

### StackAI: the one documented shell, with the most undocumented limits

StackAI's Terminal action is "Run commands in a separate StackAI computing environment", takes any command, writes under `/home/user/`, and reuses an environment's "files and installed packages" when a later step passes the earlier step's Terminal Sandbox ID ([Terminal (StackAI Computer)](https://docs.stackai.com/stackai-tools/browser-and-computer/terminal-stackai-computer.md)). That is the only documented place among the four where a workflow step can download `tsk` and `dolt`, clone a repository and run `tsk` commands against it in later steps. The page states no operating system, no network policy, no git availability, no timeout and no plan beyond "StackAI Computer must be available in your environment", and the catalog entry adds that availability "depends on your environment" and "your organization's Feature Access settings" ([StackAI Computer catalog entry](https://docs.stackai.com/integrations/catalog/stackai-computer.md)). The best evidence for git and GitHub egress is indirect: the Claude Code action, added in June 2026 to "Run Claude Code in an isolated sandbox", clones "Optional GitHub repos" with a default **600-second timeout** and a 25-step cap, and its connection takes a GitHub token for when "Claude Code opens PRs via gh CLI inside the sandbox" ([Anthropic catalog entry](https://docs.stackai.com/integrations/catalog/anthropic.md)). Whether the Terminal sandbox is the same image is not stated. Sandbox persistence is documented only "across calls" within a run; nothing says a sandbox ID is valid in a later scheduled run, so cross-run state lives in git, which is what tsk's ledger does anyway.

Unattended starts are complete. Scheduled Execution accepts daily, weekly, monthly and custom-weekday schedules ([Scheduled Execution](https://docs.stackai.com/stackai-tools/built-in-triggers/scheduled-execution.md)) and, from 16 October 2026, "cron expressions with a timezone" ([Mid-October Product Update, 16 Oct 2026](https://www.stackai.com/changelog/mid-october-product-update)); a webhook trigger verifies HMAC-SHA256 signatures ([On External Webhook](https://docs.stackai.com/stackai-tools/built-in-triggers/on-external-webhook.md)); GitHub "On Pull Request Created" and "On Release" triggers exist ([GitHub catalog entry](https://docs.stackai.com/integrations/catalog/github.md)); and `POST /v2/runs` starts an asynchronous run that a caller polls, cancels or resumes from a human-input pause, with `run.*` outbound webhooks signed in the Standard Webhooks format ([POST /v2/runs](https://docs.stackai.com/stackai-api/rest-api-v2/runs/post-v2-runs.md); [Outbound webhook subscriptions](https://docs.stackai.com/technical-reference/triggers-and-webhooks/outbound-webhook-subscriptions-and-event-payloads.md)). The execution-limits page says "There is no single timeout value that applies to every model, action, and execution path" and gives no numbers ([Timeouts and execution limits](https://docs.stackai.com/technical-reference/workflow-execution/timeouts-and-execution-limits.md)); no page gives a run ceiling, rate limit, concurrency cap or minimum schedule interval. The one published quota is the free tier's "500 runs per month*", with an unexplained asterisk, one seat and two projects; the only other tier is Enterprise at custom pricing with on-prem, VPC and SSO ([StackAI pricing](https://www.stackai.com/pricing)). Third-party trackers say the earlier $99 Builder and $499 Team tiers are gone, and one aggregator's "$120,000 a year on AWS Marketplace" is unverified ([automationatlas.io, Stack AI pricing 2026](https://automationatlas.io/answers/stack-ai-pricing-2026/); [costbench.com, Stack AI](https://costbench.com/software/ai-agent-platforms/stack-ai/)). Whether triggers, the v2 API, StackAI Computer and the Claude Code action are on the free tier is not stated anywhere; the notes infer enterprise gating from the Feature Access wording and mark it unconfirmed. Self-hosting is a licensed "50+ service Docker deployment" on Kubernetes with a minimum of 32 GB RAM and a licence key from an account manager, with no open-source repository ([StackAI on-prem CLI README](https://docs.stackai.com/stackai-auto-cli/readme.md)). The ownership risk is Asana: StackAI "continues to operate as its own product and brand" per the May release, with no public commitment to the standalone API or self-hosted product beyond that ([Asana press release via Nasdaq](https://www.nasdaq.com/press-release/asana-acquires-stackai-adding-cross-system-execution-human-agent-teams-2026-05-28)). Of the four changelog entries read in detail, only June 2026 mentions Claude Code and none mentions Terminal, and no customer story or review describes coding use ([StackAI customers](https://www.stackai.com/customers)).

## The wider field: vendor clouds fix the agent, sandboxes fix nothing, orchestrators fix the loop

The coding-agent clouds all now schedule runs against a GitHub checkout, but each fixes the agent as its own and most fix the remote as GitHub. Copilot cloud agent runs on "its own ephemeral development environment, powered by GitHub Actions", with `copilot-setup-steps.yml` allowed to set `runs-on`, `services` and `snapshot`, and "a maximum execution time of 59 minutes" that "cannot be extended or bypassed" ([GitHub Docs: Customize the agent environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment); [GitHub Docs: About Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)); its automations since 2 June 2026 run "hourly, daily, or weekly" or on issue and PR events, in private repositories only ([GitHub Docs: About automations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-automations)). Cursor cloud agents are "isolated VMs in the cloud with full development environments" built from a saved snapshot or "a Dockerfile in .cursor/environment.json", cloning from GitHub, GitLab, Azure DevOps or Bitbucket ([Cursor docs: Cloud Agent](https://cursor.com/docs/cloud-agent)), and Cursor Automations (March 2026) trigger on a cron expression, five source-control hosts, Slack, Linear, Sentry, PagerDuty or a webhook, with memory in a `MEMORIES.md` outside the working filesystem ([Cursor docs: Automations](https://cursor.com/docs/automations)). That is the widest trigger set and the only documented Dockerfile environment among the vendor clouds, so a `tsk` binary can be in the image, but the agent that calls it is Cursor's. Codex cloud documents published environments with internet presets but neither the image nor a duration cap, and a user request dated 22 October 2026 for "first-class scheduling (cron/hourly) for Codex Cloud tasks launched from a published cloud environment" indicates cloud-side scheduling was not shipped then ([Codex docs: Cloud](https://learn.chatgpt.com/docs/cloud); [openai/codex issue 56123](https://github.com/openai/codex/issues/56123)). Jules runs in a VM with daily task quotas of 15, 100 or 300 and scheduled tasks that cannot be edited ([Jules usage and limits](https://jules.google/docs/usage-limits); [Jules scheduled tasks](https://jules.google/docs/scheduled-tasks)). Devin's pricing page lists no scheduled sessions ([devin.ai/pricing](https://devin.ai/pricing)). On any of these, tsk runs only as a tool the vendor's agent calls, under the vendor's permission system and branch conventions.

Raw sandboxes and CI runners are the opposite: arbitrary binaries and a custom image, with the agent loop and the scheduler left to you. E2B bills per second at about **$0.0504 per vCPU-hour** and $0.0162 per GiB-hour, with "1 hour of continuous runtime" on Hobby and "up to 24 hours per sandbox session" on Pro at $150 a month ([e2b.dev/pricing](https://e2b.dev/pricing)). Daytona matches those rates, includes $200 of free compute, defaults to 1 vCPU and 1 GiB, requires public custom images, and auto-stops a sandbox after a "default auto-stop interval of 15 minutes" ([daytona.io/pricing](https://www.daytona.io/pricing); [Daytona auto lifecycle (mirror)](https://www.mintlify.com/daytonaio/daytona/advanced/auto-lifecycle)). Modal Sandboxes run at about $0.142 per core-hour with a "default maximum lifetime of 5 minutes" configurable "up to 24 hours", Volumes for state beyond that, and deployed crons on the platform itself ([modal.com/pricing](https://modal.com/pricing); [Modal docs: Sandboxes](https://modal.com/docs/guide/sandbox)). Fly Machines start at $2.19 a month for a 256 MB shared-CPU machine "Billed by the second while running", with no free tier ([Fly.io pricing](https://docs.fly.io/about/pricing)). Northflank's own comparison quotes itself at $0.01667 per vCPU-hour, which the notes mark as vendor-authored with no official plan page fetched ([Northflank blog](https://northflank.com/blog/best-code-execution-sandbox-for-ai-agents)). GitHub Actions gives "up to 6 hours of execution time" per job, 2,000 to 50,000 free minutes a month by plan and Linux 2-core at $0.006 a minute beyond them ([GitHub Docs: Actions limits](https://docs.github.com/en/actions/reference/limits); [GitHub Docs: runner pricing (GHES reference)](https://docs.github.com/en/enterprise-server@3.17/billing/reference/actions-runner-pricing)); the five-minute minimum schedule interval appears only in third-party guides. Per-hour prices cluster between about $0.025 and $0.08 for a small box, small next to tokens at a few runs a day. Two container standards matter for packaging: Kubernetes Agent Sandbox, a SIG Apps subproject with `Sandbox`, `SandboxTemplate` and `SandboxClaim` resources, GA on GKE since 20 May 2026 ([Kubernetes blog, March 2026](https://kubernetes.io/blog/2026/03/20/running-agents-on-kubernetes-with-agent-sandbox)), and Docker Sandboxes (January 2026), local microVMs that ship Claude Code, Codex, Gemini CLI, Copilot CLI, OpenCode and Kiro and accept custom agents ([Docker: Docker Sandboxes](https://www.docker.com/products/docker-sandboxes/)).

The orchestration platforms schedule prompts and tool calls, not a git clone with a long-running shell. LangGraph Platform lists "Cron scheduling" at $39 a seat a month plus usage in LSUs ([langchain.com/pricing](https://www.langchain.com/pricing)); Copilot Studio meters Copilot Credits at $200 per 25,000 ([Directions on Microsoft](https://www.directionsonmicrosoft.com/reports/how-microsofts-new-agent-pricing-option-affects-costs/)); Lindy, Gumloop, Relevance AI and Zapier Agents have only secondary and conflicting price figures in the notes, with no official page fetched. The exception is Foundry hosted agents, generally available on 2 June 2026 "running on Azure Developer Compute with microVM-level isolation", where "you bring a container-based agent" ([Azure update AZ563596](https://mc.merill.net/message/AZ563596)): a container with `tsk`, `git` and `dolt` is a valid deployment there. Four field-wide trends bear on a portable CLI. MCP joined the Linux Foundation's Agentic AI Foundation on 9 December 2025 with "more than 10,000 published MCP servers" ([Linux Foundation press release](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)), and every substrate here consumes HTTP MCP, while stdio MCP is accepted by Cursor and local Claude Code but not by Managed Agents ([Managed Agents reference](https://platform.claude.com/docs/en/managed-agents/reference)). A2A reached 1.0 in March 2026 and joined the same foundation in August, with adoption "mostly inside large platform vendors" ([Forbes, 19 August 2026](https://www.forbes.com/sites/janakirammsv/2026/08/19/agent2agent-joins-the-agentic-ai-foundation-alongside-mcp/)); it matters little for a single-repository CLI today. The fresh sandbox per run is the norm across routines, Copilot automations, Cursor Automations and Managed Agents deployments, which rewards tools that keep state in a remote. And credentials have moved out of the sandbox: Claude Code's GitHub proxy and network secrets, Codex's network secrets and Managed Agents vaults all keep the token outside the VM ([Cloud environments](https://code.claude.com/docs/en/cloud-environments); [Codex docs: Cloud](https://learn.chatgpt.com/docs/cloud)), and the proxies restrict pushes to branches.

## Which substrates fit tsk, which do not, and what tsk must change

Against the baseline, the substrates sort into three groups. The first runs tsk unchanged, given an install step: Claude Code cloud with routines (the baseline, missing only `dolt`); Managed Agents with scheduled deployments, at an 8 GB and 10 GB sandbox or your own worker; GitHub Actions on a cron, with a six-hour job and git and gh present; Modal Sandboxes driven by a Modal cron; E2B Pro or Daytona with a custom image and an external scheduler; Fly Machines with an external scheduler; Foundry hosted agents with a container; and a self-hosted n8n in regular mode with a custom Alpine image, `NODES_EXCLUDE="[]"` and a persistent volume. Of these, n8n is the weakest case because every piece of value it adds, cron, webhook and a run record, is reproduced by a routine or by cron on a VPS with less machinery, and its 2.0 defaults push against the use. The second group runs tsk with conditions the docs leave open: StackAI's Terminal action, which has the sandbox ID reuse, the cron and the API that a tsk run needs, but an undocumented OS, egress policy, lifetime and plan gating, and an owner whose stated plan is integration with Asana; a self-hosted Dify with the OpenShell backend, which is the one Dify configuration with an operator-controlled image, egress list and persistent mount, at the cost of a beta multi-service stack and a 3,600-second default that must be raised; and Cursor cloud agents, where a Dockerfile can carry the binaries but the agent is Cursor's. The third group does not fit as documented: Dify Cloud and the Dify E2B backend (files dropped, 3,600-second hard ceiling), n8n Cloud (no shell, 640 MiB, 5 to 40 minutes), Dust on any plan (no documented shell, allowlisted HTTPS only, "temporary"), Copilot cloud agent (59 minutes, GitHub Actions, GitHub only), Jules and Devin (fixed agent, no image control), Codex cloud (no documented image, binaries or scheduling), and the orchestration platforms other than Foundry.

That sorting answers the hosting question and reframes the builder question. Dify, n8n, Dust and StackAI are all competent schedulers with webhooks, cron, run records and MCP in both directions, and every published pattern that pairs them with a coding agent puts the agent on a machine of its own and lets the builder call it. The same holds for tsk: a runner on one of the first-group substrates, and the builder of choice as a front end that fires it (an n8n HTTP Request node can POST to a routine's API trigger today, per one comparison ([dev.to, Tariq Osmani](https://dev.to/tariq_osmani/can-claude-code-run-on-a-schedule-scheduled-tasks-vs-n8n-2gi2))) or reads and writes its ledger through tools. For a team that already holds company context in Dust or back-office workflows in StackAI, this is the integration with a documented path; for a team that does not, the builders add a subscription and a hop without adding a substrate.

Four changes to tsk would widen the set of substrates it runs on, and three of them are packaging rather than design. First, an OCI image with `tsk`, `git` and `dolt` on PATH, built for x86_64 Linux. One artefact covers Cursor's Dockerfile environments, Foundry hosted agents, Kubernetes Agent Sandbox, Modal, Daytona, E2B templates, Docker Sandboxes, a self-hosted n8n and Dify's OpenShell backend. Second, an install script that fetches the `dolt` and `tsk` release binaries and finishes inside the five-minute snapshot window and the 600-second hook budget of Claude Code cloud, and inside whatever Managed Agents allows, since neither cloud swaps its base image. The one fact to establish by test on Claude Code cloud is whether the GitHub proxy passes a release asset download for an unattached public repository; if it does not, the script needs a mirror on an allowlisted host or the repository attached to the session. Third, an HTTP MCP server over the ledger and thread commands (`mission list`, `task set`, `thread start`, `thread pause`, `ledger push`). That is the interface every substrate in this report consumes, it is what Dust's remote MCP, n8n's MCP Client Tool, Dify's MCP tools and StackAI's custom MCP connections expect, and it is the only way a tsk agent on a runner and a builder's agent can share one ledger without the builder hosting a git clone. Fourth, run-length discipline. The ceilings in the field are 600 seconds on StackAI's Claude Code action, 59 minutes on Copilot, 3,600 seconds on the Dify Agent and the n8n self-hosted maximum, 40 minutes on n8n Cloud and 24 hours on the raw sandboxes, while Claude Code cloud pauses after "a few minutes" idle and reclaims the VM. tsk's design already publishes at the hand-off points and keeps continuation state in the ledger; what the wider field asks of it is that a run can stop at any of those ceilings and that the next run rebuilds the ledger store from the remote with `tsk ledger fetch`, which the fixed store path outside the repository and the fresh-clone bootstrap already support. The local Dolt server's 1,800-second idle stop outlives several of these ceilings, so a run on a short-lived sandbox should stop the server before it ends, or the sandbox does it for it. The branch-only push rule is already handled by the `refs = "branches"` setting, and it is the pattern that survives across the proxies in this field.

## Conclusion

The hosted builder segment and the coding-agent segment separated in 2026 along the line that matters for tsk: whether the product gives an agent a Linux filesystem for the length of a run. The four builders chose the per-step sandbox, the credit meter and the connector catalogue, and the capital events of the year (SAP into n8n, Asana over StackAI, Sequoia into Dust, HSG into Dify) reward that choice; the shells they added in 2026 are tools for a business agent to make a spreadsheet, not a place to keep a clone. The substrates that fit tsk are the ones with the least product on top of the box, and the price of that box is now small enough, under a dollar per running hour on every option, that the choice between them is about the proxy, the ceiling and the image, not the bill.

The practical consequence for tsk is that portability is a packaging exercise plus one interface. A tsk image and a sub-five-minute install script reach every substrate with a shell, and an HTTP MCP front end on the ledger lets every substrate without one still take part. The open facts to settle are small and testable: whether the Claude Code GitHub proxy serves a `dolt` release asset, what OS and egress StackAI's Terminal sandbox has, and whether StackAI's and Dify's cloud tiers expose the shell at all. Until those are known, the baseline stays the only substrate where tsk's full model, a session-long clone with the ledger published at the hand-off points, is documented end to end.
